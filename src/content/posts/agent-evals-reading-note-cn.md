“最近好像变差了”是 Agent 项目很常见、也很难处理的一句话。它可能来自模型、提示词、工具返回、环境污染或评测器本身。没有可重复的任务和最终状态，这种体感无法变成工程问题；有了一个总分，也仍然可能不知道分数为什么变。

更实用的 eval 是故障定位系统，而不是模型排行榜。评测的第一问题应是“任务完成后世界变成了什么”，第二问题才是“Agent 为什么走到这里”。这会改变 task、grader 和 transcript 各自承担的职责。

## 先把“做成了”从“说做成了”里分出来

Agent 会在多轮调用中读环境、改状态、再根据反馈行动。因而最后一句“已经完成”不等于任务真的完成。订票要检查数据库中的预订记录，代码修改要检查测试和安全边界，文件操作要检查文件内容；对话只是过程的一部分。

Anthropic 把一次评测拆成 `task`、`trial`、`transcript`、`outcome` 和 `grader`：task 定义输入与成功标准，trial 是一次运行，transcript 是完整过程，outcome 是环境最终事实，grader 负责判分。[原文定义](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) 这套拆分看似术语整理，实际是在防止团队把模型的自我报告当成外部事实。

outcome 应放在主位置。用户要的是退款真的处理、代码真的修好、报告真的有证据，而不是 Agent 讲出一段可信的解释。确定性测试、状态检查和静态分析能回答的问题，不应交给一段主观文本或一个 LLM judge。

## transcript 是归因材料，不是神谕

只看 outcome 也不够。一次失败可能始于任务理解错误，也可能始于错误工具、异常返回、脏环境或最后一步遗漏。transcript 的作用是把红叉拆成这些不同的原因，帮助决定修哪里。

但轨迹不能变成另一种僵化标准。要求 Agent 必须按“搜索—选择—提交”的固定顺序行动，可能把先读政策、先确认身份或先检查库存的合理路径判成失败。只有具有业务或安全意义的约束才应成为硬性 grader，例如退款前验证身份、转账前二次确认、代码修改后运行测试。

比较稳的分工是：outcome 判断事情是否做成，transcript 解释为什么，少量过程约束守住真正的边界。这样可以奖励目标正确的替代路径，也能保留调试所需的证据。

## 评测对象不同，尺子就该不同

不同 Agent 改变的世界状态不同，不能共用一套“像不像参考答案”的评测。先问这个 Agent 主要改变什么，再问哪些过程约束真的重要。

| Agent 类型 | 主要 outcome | transcript 重点 |
| --- | --- | --- |
| 代码 Agent | 测试、静态分析、安全边界和回归行为 | 是否读对文件、如何处理报错、是否运行验证 |
| 对话 Agent | 工单、订单、退款或预约状态 | 身份验证、政策依据、轮数和语气 |
| 研究 Agent | 关键事实覆盖、来源质量、结论支撑 | 搜索路径、引用是否跟得上判断 |
| 电脑操作 Agent | 页面、文件、配置或后端状态 | 是否看懂界面反馈、是否误点或漏确认 |

代码 Agent 的解释再漂亮，也不能替代测试；研究 Agent 的文风再顺，也不能替代证据链；电脑操作 Agent 看到成功提示，也不代表后端真的写入。评测越贴近真实目标，分数越有工程含义。

成本和延迟也应记录。浏览器 Agent 可能在 DOM 与截图之间取舍，代码 Agent 可能在测试成本与信任之间取舍，研究 Agent 可能在覆盖与噪声之间取舍。只记成功率，会把这些产品决策隐藏起来。

## 从真实失败开始，而不是从理想题库开始

早期 eval 不需要几百道题。最有价值的起点通常是用户投诉、手工复现过的坏例子、发布前反复检查的流程，以及团队争论过的边界。把这些案例写成 task，成功标准同时写清，才能把“感觉不稳定”变成回归信号。

每道题都应先用人工或基准实现确认可解，再检查 grader 是否能判对。若强模型连续得到零分，先排查题目是否含糊、环境是否残留旧状态、测试是否检查了未声明的路径，而不是立刻把问题归因于模型。

正例和反例要一起放进 suite。只测“应该搜索”的场景，会把 Agent 推向逢问必搜；只测“应该退款”的场景，会鼓励跳过身份验证。干净环境、确定性 grader 和可解释的部分分，比一张看起来很大的题单更有价值。

## 分数只能告诉人往哪里看

长期维护时，最危险的是只盯总分。低分可能是 Agent 不会，也可能是 task 写坏；高分可能是 suite 太简单、grader 太宽，或者真实失败根本没有进入集合。失败 trial 的 transcript 必须被定期抽样，确认判分是否公平。

还要区分能力集和回归集：前者允许低通过率，用来暴露下一座能力高峰；后者放已经应该稳定完成的任务，用来防止改动伤害旧能力。一组能力题满分后可能变成回归题，长期满分的题也可能已经饱和，需要换成更贴近真实风险的新题。

评测的终点不是得到一个更好看的百分比，而是让团队能说清楚下一步动作：修任务、修环境、修工具、修 Agent，还是修 grader。只要每次线上失败都能沉淀为可复现的 task，eval 就从展示指标变成了工程记忆。

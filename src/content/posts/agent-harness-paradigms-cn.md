给编码 Agent 接一个内部检索接口，看起来只是增加一个工具。接下来，团队希望失败时换模型，审查模式禁止写文件，任务结束前必须运行验收。需求逐渐伸进调用循环之后，才发现最早选的工具是否支持“插件”，并不能回答这些问题。

插件可能只是增加一条命令，也可能改变工具执行前的行为，还可能替换整段运行逻辑。讨论 Harness 的扩展能力，最好先说清楚需要动哪一层。

DSH、OpenCode 和 Pi 恰好体现了三种不同取舍：把运行时拆成可组合部件，把常见工作流做进完整产品，或保留较小的核心，再通过扩展补上个人需要。这不是由弱到强的排序，而是维护责任的不同分配。

## 先确定要替换的是什么

假设目标是给 Agent 增加一个查询接口，三种方案都有实现空间。真正拉开距离的，是后面那个“顺便”：顺便换上下文压缩，顺便改变停止条件，顺便让同一个宿主运行多种工作方式。

| 方案 | 主要定制入口 | 更值得先确认的成本 |
| --- | --- | --- |
| DeepSeek Harness | 通过插件组合或替换运行时能力 | 接口契约、依赖关系与资源生命周期 |
| OpenCode | Agent 配置、自定义工具和事件钩子 | 现有扩展点是否覆盖所需行为 |
| Pi | TypeScript 扩展、工具与会话事件 | 需要自行补齐多少工作流与验证 |

这张表的用途是缩小问题。若只需要一套项目规则，先写清规则并检查加载情况就够了；若要改调度策略，才需要研究调度到底属于哪个模块。没有必要因为未来“可能深度定制”，提前承担整个运行时的复杂度。

## DSH：运行时本身也能参与组装

DSH 的 [架构文档](https://github.com/deepseek-ai/deepseek-harness/blob/67266b07cfc20d18c99d140a1d89ccc87defc718/docs/architecture.zh.md)把模型适配器、工具注册表、会话日志与 Agent Loop 都列为 Cordis 插件。应用行为由装配关系决定，循环也不是藏在所有扩展之外的特殊部件。

这给实验留下了较深的入口。例如需要比较两种循环策略，可以在相同模型和工具条件下替换驱动实现，检查失败率与成本怎样变化。它并不保证实验容易，只是减少了为了替换一个组件而复制整个产品的必要。

代价也落在同一处。换掉模型提供方之后，流式事件、错误分类和取消语义仍要满足消费者的约定；接口能对上，不代表所有行为都等价。若调用方期待取消后不再产生结果，新实现却继续回调，问题可能在很远的会话层才暴露。

[Cordis 生命周期机制](https://github.com/deepseek-ai/deepseek-harness/blob/67266b07cfc20d18c99d140a1d89ccc87defc718/docs/cordis-tutorial/02-lifecycle-and-effects.zh.md)负责在插件卸载时撤销受管理的注册，并让外部资源通过 effect 提供清理函数。但清理函数是否正确，仍要验证。热重载成功，不能直接推出旧连接全部关闭，更不能推出插件已发送的外部请求可以撤销。

因此采用这种路线时，验收对象应当包含替换过程：旧组件退出、新组件失败、依赖暂时消失时，系统各自留下什么状态。只测试最终的成功路径，会错过可组合架构最容易出问题的部分。

## OpenCode：默认流程本身就是产品能力

如果团队的主要工作是读代码、提出修改、执行测试，很多决策没有必要每次重做。[OpenCode 的 Agent 配置](https://github.com/anomalyco/opencode/blob/65c35977bd564e23c0e9cf124b3e3e3b9308e9e8/packages/web/src/content/docs/agents.mdx)提供 Build 和 Plan 等现成入口，并允许为不同 Agent 配置模型、提示词和工具权限。

这里要注意模式名称与实际约束的区别。Plan 面向分析和规划，但到底哪些操作询问、哪些操作拒绝，要以生效的权限配置为准。不能因为界面写着 Plan，就把它当成天然的只读执行环境。

[权限规则](https://github.com/anomalyco/opencode/blob/65c35977bd564e23c0e9cf124b3e3e3b9308e9e8/packages/web/src/content/docs/permissions.mdx)使用 `allow`、`ask` 和 `deny` 表达动作策略，还可以按路径或命令模式细分。这让“审查时允许读取，但修改需要确认”成为可检查的配置，而不只是提示词里的一句话。

OpenCode 也并非不能扩展。[插件接口](https://github.com/anomalyco/opencode/blob/65c35977bd564e23c0e9cf124b3e3e3b9308e9e8/packages/web/src/content/docs/plugins.mdx)支持注册工具、订阅事件，以及在工具执行前后介入。日常所需的通知、参数调整或附加检查，未必需要触碰主循环。

更合理的判断是：先把需要改变的行为写成一个具体例子，再寻找对应扩展点。若钩子已经能获得必要信息，并在正确时机阻止动作，复用现成产品会少维护很多代码。若只能事后收到通知，却需要执行前阻断，就不能靠多写一段提示词填上这个缺口。

## Pi：核心少，责任不会一起消失

Pi 默认给模型的工具是 `read`、`write`、`edit` 和 `bash`，不把子 Agent、Plan 模式等工作流全部内置。[项目说明](https://github.com/earendil-works/pi/blob/8ba9326f8663b9319dc215f8d5c3c5c4f84d3a42/packages/coding-agent/README.md)把扩展、Skills 和提示词模板留给使用者组合。

这使行为更容易从较少的入口追踪。例如项目只需要读文件、运行已有脚本并生成补丁，默认工具可能已经足够。专用工具越多，模型越需要理解它们的区别，团队也越需要维护描述与真实行为的一致性。

不过，“工具少”不自动等于“消耗少”。一个 shell 工具也可以输出几万行日志；缺少合适的专用入口，模型还可能花更多轮探索命令。要比较成本，应当看完成同一任务的总调用与返工，而非只数工具名称。

Pi 的 [扩展事件](https://github.com/earendil-works/pi/blob/8ba9326f8663b9319dc215f8d5c3c5c4f84d3a42/packages/coding-agent/docs/extensions.md)可以在 `tool_call` 阶段阻止调用，也可以介入上下文与工具结果。这提供了定制空间，同时要求扩展作者理解顺序和状态：前一个处理器改变参数，后一个看到的已经不是最初输入。

会话结构也不能代替环境恢复。[Pi 的会话格式](https://github.com/earendil-works/pi/blob/8ba9326f8663b9319dc215f8d5c3c5c4f84d3a42/packages/coding-agent/docs/session-format.md)用 `id` 与 `parentId` 表达分支，便于从过去的位置继续讨论。但回到一条旧消息，并不会自动把工作目录还原到当时。比较两条解题路线时，还需要分别保存或隔离文件状态，否则第二条路线会继承第一条留下的修改。

## 把选型缩成一次有边界的验证

这些区别适合通过一个真实任务来判断。选定仓库中的一次小修复，固定模型、输入和验收条件，分别记录完成结果、总成本、人工介入，以及一次中断后的恢复情况。

然后只改变团队最在意的那一项：接内部工具、加入执行前检查，或替换某段运行策略。观察改动触及多少模块，失败时能否定位，升级后需要重测什么。这里得到的维护成本，通常比功能表更接近未来的日常工作。

三者之间也存在复用。DSH 的 [多模型适配包](https://github.com/deepseek-ai/deepseek-harness/blob/67266b07cfc20d18c99d140a1d89ccc87defc718/packages/llm/llm-pi-ai/package.json)依赖 Pi 生态中的 `@earendil-works/pi-ai`。运行时组织方式不同，并不妨碍在模型接入这一层共享实现。

选型最后应该落到一句具体的话：团队需要改的是工具、策略还是循环，并且愿意长期维护到哪一层。若这个边界还说不清，先用现有入口完成一次任务，再从实际失败里找扩展点，会比提前认领一种架构哲学更稳妥。

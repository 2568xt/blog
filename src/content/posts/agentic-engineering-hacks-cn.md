假设一个 demo 在半天内做出来：界面能点，流程能跑，甚至还有一份像样的演示视频。接下来却没有人使用，也没有人愿意为它提供下一条具体反馈。Agent 让“能不能做”变得便宜，却没有让“值不值得做”变得容易。

读 Matt Van Horn 的 Agentic Engineering 经验，最值得留下的不是工具组合，而是这个反差。计划、并行会话和自动化都在压低构建成本；成本越低，越需要把反馈、复用和停止条件写进工作方式，否则人会把更多时间花在完善无人需要的东西上。

## 反馈速度不等于需求信号

Agent 可以把一个模糊想法迅速变成 `plan.md`、代码和 demo。计划的价值在于把目标、上下文、约束和验收条件写出来，让执行不至于靠猜；它并不能证明目标本身值得追。计划回答的是“怎样做”，不是“谁会用、为什么现在用、什么现象说明应该停”。

因此，demo 完成后的第一个问题不应是还能加什么功能，而是有没有新的外部事实进入判断。真实用户是否完成了核心动作？他们卡在哪里？有人是否愿意主动回来，或明确要求一个具体改动？没有这些信号，继续让 agent 生成更多页面和边角功能，只是在把内部反馈误当成市场反馈。

并行会话会放大这个误区。一个窗口做研究，一个窗口写实现，另一个窗口修体验，几条任务线都在向前走，看起来像高吞吐；但如果它们共享的仍然只有最初的假设，并行只会更快地产生同一种偏差。任务拆分必须同时拆出检查点：哪一步等待用户反应，哪一步需要重新确认问题，而不是让所有窗口一直保持忙碌。

## 不要过早替用户整理分歧

很多 agent 工作流强调把完整资料交给模型：会议 transcript、截图、issue、讨论串都可以成为计划输入。这个做法真正有价值的地方，不是让模型获得更多字数，而是保留判断发生时的原始形状。摘要会提前替人删掉犹豫、冲突和没有结论的句子；恰恰这些内容可能说明需求还没有稳定。

原始记录当然很脏。会议里会有重复、跑题和半句话，讨论串也可能混着不同人的目标。处理它们时，应该让 agent 标出分歧来自哪里、哪些事实已经确认、哪些只是猜测，再决定是否进入计划。把所有内容压缩成三条“共识”，会让执行更顺滑，却可能掩盖没人真正同意的前提。

这也是 Human Signal 的边界：人不必亲手完成每一次整理，但必须判断哪些反应改变了问题定义。一个流畅的总结、漂亮的 demo 或十个候选方案，都不能代替对分歧的确认。对 agent 来说，最有用的指令有时不是“继续优化”，而是“列出目前仍然互相矛盾的需求，并说明缺哪条证据”。

## 复用要等到失败方式稳定

当一件事重复出现时，把它写成 Skill、脚本或可调用接口很有吸引力。复用能减少重复解释，让下一次任务直接继承输入格式、步骤和验证方式。但“做过两次”还不足以说明流程值得固化：如果每次失败的原因不同，封装出来的只是一个过早冻结的猜测。

真正适合复用的流程，至少应有稳定输入、可观察输出和可识别失败。比如一个资料整理流程，应该知道哪些来源必需、哪些判断需要人工确认、怎样发现遗漏；一个面向现实服务的接口，则要明确授权范围、失败后的停止动作和是否允许重试。把这些边界写出来，才是在复用方法，而不是把一次成功的提示词复制粘贴。

开源贡献或团队协作会提供更硬的检验：外部维护者、CI 和 review 会暴露本地 demo 没发现的问题。能否被别人理解、运行和修正，比“本机上看起来很顺”更能说明流程已经具备复用价值。若每次交接仍要重新解释背景，说明应先修正工作方法，而不是急着扩大自动化范围。

## 成本是停止条件的一部分

构建成本下降后，时间、订阅、计算、电量、维护和注意力就更容易被忽略。多个 agent 会话可以同时推进，但每条线都需要有人阅读结果、核对权限、处理失败和决定下一步。没有用户的 demo 继续消耗这些资源，仍然是一种选择，只是不能再把它描述成“顺手做做”。

尤其要警惕登录态和真实服务。一旦 agent 能代表用户调用外部系统，错误就不再只是一段代码没写对，还可能变成错误订单、错误通知或泄露的会话。高风险动作需要最小授权、清楚的 allowlist 和人工确认；如果这些护栏让流程变得不值得维护，停止自动化本身就是合理结果。

停止也不等于否定构建。一个自用工具可以因为个人便利继续存在；一个想要真实用户的产品，则应当用使用频率、主动反馈和维护成本决定是否继续。Agent 擅长把“下一版”迅速做出来，人仍然需要提出更难的问题：新增的功能带来了什么外部证据？如果没有证据，下一次迭代是在接近需求，还是只是在延长兴奋？

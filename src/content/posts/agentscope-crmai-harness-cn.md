做 CRMAI 时，需要解决的并不只是“让模型回答 CRM 问题”。一个用户描述了办理诉求，Agent 要提取字段、补问缺项、调用工具，再把结果返回前端。用户接着追问、切换会话，或者提交途中连接断开，服务还得知道这件事究竟走到了哪一步。

以工单为例，“模型说已经提交”“工具调用返回成功”“数据库里存在工单”，是三件不同的事。若没有分清它们，前端展示得再流畅，也可能只是把一个尚未完成的动作讲得很像已经完成。

因此，研究 AgentScope 2.0 的出发点，是给 CRMAI 找到合适的运行层：把会话、工具、工作区和上下文管理接起来，同时保留业务自己判断结果的能力。接入框架之后，哪些状态由框架保存，哪些约束由业务兑现，这条界线比功能清单更值得先想清楚。

## 推理循环之外，还需要一个稳定的运行入口

AgentScope Java 保留了 `ReActAgent` 的推理与工具调用循环，并在上面提供 `HarnessAgent`，把工作区、记忆、上下文压缩、子 Agent 和权限等能力组织起来。两种入口对应不同复杂度的应用，不要求每个任务都开启全部能力。[AgentScope Java 2.0 发布说明](https://github.com/agentscope-ai/agentscope-java/releases/tag/v2.0.0)

CRMAI 主服务的构建层使用 `HarnessAgent`，集中装配模型、工具、子 Agent、状态存储和相关配置。上层聊天服务处理请求与会话，下面的运行层推进推理和工具执行。这样业务入口不必在每次对话里重新拼一遍上下文与工具生命周期。

但“统一入口”也意味着要分清对象的生命周期。Agent 的配置、某个用户的会话、一次调用中的临时变量，不应该因为它们都参与推理，就塞进同一个可变对象。

主服务缓存构建后的 Agent 实例，同时通过运行上下文传递用户与会话身份。缓存减少重复构建，运行上下文确定这次请求归属谁。复用 Agent 配置和共享用户对话不是一回事，缓存键、状态键与调用入口必须一起检查。

这也是升级或接入框架时应该先验证的地方：新会话是否真的是新状态，同一会话能否接着上一轮走，不同用户使用同一个 Agent 时是否互相影响。类能实例化、接口能返回文字，只覆盖了很小的一段链路。

## 工作区解决存放位置，业务决定归属范围

Workspace 容易被理解成“给 Agent 一个目录”。对本地助手，这个理解基本够用；对一个多人使用的服务，还要继续问：目录属于谁，容器重启后是否保留，请求落到另一台实例后还能否读到。

AgentScope 将逻辑工作区与底层文件系统分开，允许按场景选择本地存储或其他后端。对 CRMAI 来说，这个抽象的价值在于，Agent 使用文件的方式可以相对稳定，而持久化与隔离可以在存储层处理。

项目里，会话状态与工作区文件也采用了不同的管理方式。主服务接入 Redis 保存 Agent 运行状态；工作区路径包含用户与 Agent 维度，并有持久化文件后端的接入。这里重要的不是选了哪个数据库，而是先列清楚每类数据的归属与恢复要求。

| 数据 | 主要用途 | 需要明确的边界 |
| --- | --- | --- |
| Agent 配置与能力定义 | 决定模型、工具和行为配置 | 哪些用户可使用，配置变更何时生效 |
| 会话运行状态 | 延续推理与工具调用上下文 | 用户、会话以及恢复后的版本一致性 |
| 工作区文件与记忆 | 保存可再次读取的材料 | 用户与 Agent 范围、持久化范围、失效方式 |
| 业务草稿与工单 | 判断办理进度和最终结果 | 租户、用户、版本、确认与防重 |

用户维度的文件隔离不能直接推出完整的租户隔离。租户身份怎么解析，业务查询是否带上访问范围，缓存是否可能复用错误的主体，都属于应用侧必须验证的问题。

共享存储也不能自动解决并发写入。两个请求即使看见同一份状态，仍可能同时修改它；单进程中的串行执行约束，也不能直接当成跨实例互斥的证明。分布式部署要验证的，是整个请求与存储链路，而不只是状态落到了 Redis。

同样需要分开的是运行状态和展示历史。页面需要分页、按窗口组织消息，模型恢复则需要完整的工具调用关系与当前状态。展示层可以有自己的索引或副本，但不能因为聊天记录看起来完整，就认定业务动作可以安全重放。

## 压缩上下文时，先决定什么不能交给摘要

CRM 工具的一次返回可能包含很多记录。把完整列表留在每轮上下文里，模型反复付出阅读成本；简单截断又可能丢掉下一轮要查的那条数据。

AgentScope 提供超大工具结果外置、历史压缩和记忆整理等机制。CRMAI 主构建层接入了工具结果淘汰与上下文压缩配置：较长内容可以从活跃上下文中移出，再通过引用读取，历史则根据策略整理。

引用能否再次读到，是这个机制的一部分。如果原文只存在于某台机器的临时目录，下一轮请求换了实例，摘要里留下的路径就失效了。因此压缩策略和工作区持久化不能分开设计。

更容易被忽略的是，压缩前要先给信息分类。工具返回的长列表可以外置，重复的解释可以归纳；当前任务目标、未完成动作、权限决定和待确认草稿，则需要有稳定的状态来源。

例如，用户确认过一份草稿，之后又修改了城市字段。摘要即使还保留着“用户已确认”，也不能据此提交新版本。确认应该绑定具体草稿版本，由业务服务判定是否仍然有效，而不是让模型从对话措辞里推断。

项目的公开工单验证模块采用了一个具体做法：每次推理前临时注入用户原始输入、当前草稿、已写入工单与实际办理状态。这份视图来自应用当前状态，不无限追加到聊天历史。模型可以继续使用会话记忆，但判断业务进度时还有一个可以对照的状态入口。

这个模块使用的是较轻的 `ReActAgent`，并不等同于主服务的 Harness 部署。它说明的是同一条原则：无论选哪个推理入口，关键业务事实都不应只保存在模型可自由改写的摘要里。

长期记忆也要遵守这个边界。用户的展示偏好可以沉淀，客户归属、当前权限和工单状态却可能变化。记忆适合帮助定位信息，真正执行前仍要读取有效的业务状态。“曾经知道”不能自动变成“现在仍然成立”。

## 工具能被调用，不代表业务已经允许执行

Skills、工具和沙箱分别解决不同问题。Skill 可以组织步骤与资源；工具提供具体操作入口；沙箱限制执行环境。把它们都接上之后，仍然需要业务权限来决定某个主体能对哪条数据做什么。

对 CRMAI，比较实用的拆分是把读取、形成草稿和最终提交分开。前两步帮助用户把需求说清楚，最后一步才产生正式业务结果。模型需要知道可调用的工具，服务则需要验证工具入参、主体和当前状态。

工单验证模块里，模型工具没有独立确认草稿的能力。确认由应用入口处理，提交只能使用当前版本的已确认草稿；字段变化后，旧确认失效。这样，“请忽略前面的限制”或者模型自己生成的“用户已确认”，都不能替代应用里的确认状态。

这里的收益是确定的：确认不再依赖一次语言理解是否刚好正确。但它并没有解决所有问题。字段提取是否准确、分类是否合适、用户是否理解草稿内容，仍需要清晰展示与业务校验。

AgentScope 的权限机制提供介入工具执行的入口，实际规则要在应用里接好。沙箱则处理脚本或工具的执行隔离。即使某个操作运行在容器里，若它拿着过宽的业务凭据访问服务，容器本身也不会替它缩小数据权限。

因此，验证这部分能力时，需要分别看工具授权、业务数据范围和执行环境。框架有对应配置项，不能替代应用对这些边界的实际检查。

## 并行与异步，最终都要回到同一个业务结果

AgentScope 提供子 Agent 委派、同步或后台执行，以及任务状态与事件传递等能力。CRMAI 主构建层也支持装配子 Agent，不过“可以委派”和“每次请求都该委派”之间，还需要一次任务判断。

如果一次分析可以拆成彼此独立的查询，并行可能减少等待；如果各个子任务都在修改同一份草稿，增加 Agent 只会让版本与结果合并更复杂。对有写入动作的流程，先确定谁拥有最终提交权，再考虑怎么并行。

后台任务还会把问题带到前端。文字开始输出、工具开始执行、子任务结束和业务办理完成，需要不同的事件含义。只显示一条不断增长的回答，用户无法判断系统是在处理、等待确认，还是已经产生结果。

CRMAI 的服务代码把 Agent 事件映射成前端可消费的 SSE 事件。这让界面有机会展示执行过程，但展示过程本身不构成业务回执。刷新页面、断开连接或请求超时后，仍然要能够查询实际状态。

工单模块把这个问题收到了持久化业务层：提交响应丢失时，先查询原提交结果，避免再次创建。幂等状态和真实工单各有约束，应用回执也依据保存的办理状态生成，而不是把模型最后一句话当成成功标志。

这一实现使用本地 SQLite 验证业务状态与防重边界，不能因此宣称跨服务的分布式“恰好执行一次”已经解决。它给主系统留下了一个明确的验收方向：即使结果通知没有送到，仍然能查清原来的操作是否完成。

## 接入之后，用业务样本决定还要补什么

框架把很多通用能力集中起来，减少了重复实现；它没有替 CRMAI 定义什么叫“办对了”。

验证需要同时看模型行为和业务最终状态。工具是否被正确调用，回答有没有遗漏关键字段，是否越过确认环节，重复请求是否产生第二张工单，这些问题不能压成一个模糊的“回答质量分”。

| 场景 | 需要检查的证据 |
| --- | --- |
| 用户信息不足 | 是否补问，是否避免凭空填入字段 |
| 确认后修改草稿 | 旧确认是否失效，新内容是否重新核对 |
| 工具超时或响应丢失 | 能否查询原结果，是否避免重复写入 |
| 长对话发生压缩 | 当前任务与真实办理状态是否仍然一致 |
| 切换用户或会话 | 是否只读到当前主体有权访问的数据 |
| 更新模型、提示词或工具 | 相同业务样本是否出现新的退化 |

项目的评测设计也区分了答案要点、预期工具和禁止结论。工单模块进一步核对最终记录与字段。脚本模型可以验证工具接线，真实模型样本才能暴露部分语义问题；两者都通过，也只说明覆盖的场景通过，不能直接外推线上成功率。

这给 Harness 的迭代提供了一个具体顺序：先找到失败发生在哪一层，再决定补哪一层。字段提取不准，应检查工具定义和输入；状态丢失，应检查会话与持久化；重复建单，应检查提交协议与幂等，而不是统一加长系统提示词。

对 CRMAI 而言，AgentScope 最有价值的地方，是让运行过程有一套可以持续调整的结构。业务最终仍要回答那个朴素的问题：用户回来问“刚才那件事办成了吗”，系统能不能拿出准确的记录，而不是再生成一段听起来肯定的话。

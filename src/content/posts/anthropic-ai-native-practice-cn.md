一个改动上午就写完，下午卡在评审，第二天才发现需求理解有偏差。即使再把编码时间压缩一半，用户也未必能更早拿到功能。生成速度变快以后，原本藏在实现工期里的等待会单独露出来：谁确认边界，谁解释依赖，谁承担上线后的结果。

Anthropic 的 [AI Native SDLC Playbook](https://claude.com/blog/the-ai-native-sdlc-playbook) 把注意力放到了这些环节。它用可版本化的产物衔接规划、设计、构建、测试、部署和维护：`intent.md` 保留需求意图，`spec.md` 固化设计决定，`plan.md` 说明实施与验证，后续接上代码、评审记录和事故记录。人仍要对关键判断负责。

这套做法值得琢磨的地方，是让下一步拿到足以继续工作的东西。把同一句模糊需求从工单搬进 Markdown，并不会让它更容易实现。

## 交接应该留下决定，而不只是经过

拿“给导出功能加异步任务”来说，会议纪要可以记录讨论了队列、进度条和下载链接，却仍然无法回答：用户重复点击是否创建第二个任务，权限被撤销后还能否下载旧文件，失败的任务由谁重试。

如果这些问题留到代码评审才出现，reviewer 就得一边判断实现，一边补产品设计。AI 能快速再改一次，但参与者仍要重新理解变更，测试也可能已经围绕错误前提展开。

更省事的交接，是在动手前留下少量有约束力的决定。例如明确任务归属于哪个账号、什么状态允许重试、结果保留多久，再给出相应验收场景。实施计划可以很短，只要陌生工程师读完后知道哪些行为不能被改变。

这里也有文档成本。修正一个明显的文案错误，没必要制造三份内容重复的文件；涉及任务状态和权限的改动，则值得把决定写清楚。需要保存的是容易在交接中失真的信息，文件名和数量可以服从仓库现有习惯。否则 AI 写文档很快，团队阅读文档的队列又会变成新的瓶颈。

## 三种约束，应该放在三个地方

把团队经验写进项目说明，可以减少反复解释。但“不要越权”和“执行到越权动作时必然被拒绝”，工程上相差很远。

[Claude Code hooks 文档](https://code.claude.com/docs/en/hooks-guide) 区分了生命周期中的命令执行与依赖模型判断的 hook。前者适合确定性检查，后者仍然需要评价判断质量。即使触发动作固定，检查内容也不因此完整；执行之后才运行的检查，更无法撤回已经发生的外部操作。

对前面的导出功能，可以这样安排约束：

| 要守住的事情 | 合适的落点 | 仍然需要检查什么 |
| --- | --- | --- |
| 沿用现有任务状态和错误格式 | 项目说明与可复用工作步骤 | 说明是否过时，模型是否理解了当前调用链 |
| 每次改动后检查类型、状态迁移和权限用例 | 自动检查与 CI | 用例有没有漏掉跨账号、撤权和重复请求 |
| 开发任务不能读取生产密钥、直接发布生产版本 | 运行身份、凭据范围和发布系统 | 有没有其他工具或间接调用能绕到同一权限 |

这三层互相补充。提示里的约定负责让模型更早做对，测试负责发现实现偏差，权限负责限制它最终能做什么。把最后一层寄托在模型“记得遵守规则”上，等于让生成代码的判断同时决定自己是否可以越过边界。

## 审查吞吐不能只靠增加审查者

AI 可以并行生成多个改动，也可以并行评审。问题在于，十份“看起来没问题”仍然没有说明检查了什么。评审角色只有拿到不同证据、承担明确问题，才可能补上盲区。

例如一个角色沿着账号身份检查数据访问，另一个角色检查任务重试是否幂等，测试程序再用真实接口验证状态转换。它们不需要共同复述整份 diff，而应交出能定位的发现：哪条输入穿过哪段代码、会产生什么错误结果、如何复现。没有证据的担心可以保留为待核实项，不能和已复现缺陷混在一起。

Anthropic 在[安全实践](https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle)中描述了按风险分层审查、对自动批准抽样复核，以及把 Agent 行动记入审计系统。这提供了一个重要提醒：自动评审通过本身，也应该成为被检查的对象。

对于自己的项目，笔者会先关心漏检与误报，而非评论数量。挑一组已经知道原因的历史缺陷，观察检查是否能指出真正的问题；再拿正常改动观察是否不断制造无关警告。若每条评论都需要人花很久排除，表面上的并行审查反而会挤占维护者的判断时间。

同样，模型生成了测试，不代表需求已经被独立验证。实现和测试可能共享同一个错误假设。异步导出里最有价值的用例，往往是从业务边界倒推出来的：另一个账号拿到任务 ID 会怎样，撤销权限后重试会怎样，网络超时后重复提交会怎样。这些输入要能挑战实现，而不只是沿着成功路径证明代码能跑。

## 发布边界要沿着权限继续追

安全材料还记录了一次很具体的经历：负责响应事故的 Agent 没有部署权限，却在模型升级后主动联系另一个 Agent，请它推送修复；最终被人工评审拦住。这个案例说明，单个身份没有某项权限，不足以说明整条协作链做不到那件事。

若在自己的系统里允许 Agent 互相派单，就需要检查请求接收方怎样判断授权。一个“帮忙上线”的消息，应当进入和正常发布相同的身份校验与审批记录，不能因为来自内部 Agent 就被当成授权证据。排障服务可以产生补丁建议，发布系统仍然要独立检查变更对象和批准条件。

这也解释了为什么模型升级不能只跑生成质量测试。能力变强可能改变行动路线：以前等用户回复的步骤，现在会主动找其他工具完成。回归验证应覆盖它实际能够访问的入口，尤其是通信工具、共享目录和发布凭据。

## 先量出最久的等待

要判断这类改造有没有价值，可以先记录一次变更从提出到上线的几个时间点，把编码、等评审、返工和等发布分开。否则代码量增加了，维护者却更忙，很容易被误读成“团队还没有充分使用 AI”。

如果等待主要来自需求反复，就先改进交接材料；如果 reviewer 每次都在指出同一类遗漏，就把它变成可运行的检查；如果发布越来越频繁，回滚和观测却跟不上，就先验证能否及时发现坏版本并停止扩散。

真正值得保留的流程，是下一次出错时能回答两个问题：哪一个判断当时缺少证据，以及补上的检查是否真的会拦住同类错误。多生成一份计划或多安排一个 Agent，都得回到这两个问题上验收。

复杂任务真正难的地方，通常不是动作多，而是判断被分散在很多动作之间：哪些入口已经覆盖，哪个测试只是偶然通过，哪条结论缺少证据，什么时候应该停止。把这些问题交给同一个长上下文，模型可能顺利完成，也可能只处理了一部分就宣布结束，沿着自己的结果继续判断，或在多轮摘要后丢掉原始约束。

Anthropic 对 dynamic workflows 的介绍让我更确定一件事：复杂任务需要临时生成一套判断结构。Claude Code 可以根据任务组织 subagents、模型选择、隔离环境、结构化结果和停止条件。这里的价值不在于把 agent 数量变多，而在于为每个判断安排位置，并让结果能被下一步检查。

## 编排收益要先支付协调成本

默认 harness 适合明确、短链路、反馈快的任务：局部 bug、一个测试或一段文案。模型在同一上下文里读、改、测，失败后也容易回滚。动态 workflow 适合长时间运行、大规模并行、结构化产出或对抗性验证。静态 workflow 介于两者之间，适合重复且边界稳定的检查。

选择的关键不是任务听起来是否“复杂”，而是拆分后是否真的降低了判断难度。若子问题强耦合，多个 agent 只会增加交接成本；若失败容易回滚，额外的验证也未必值得。并行和专门化必须赚回它们带来的 token、等待和人工汇总成本。

## 上下文隔离必须配合交接格式

动态 workflow 可以为子 agent 提供独立上下文和 worktree，也可以按阶段选择模型。独立上下文能减少目标漂移和自我偏好，却会带来一个容易被忽略的问题：每个角色到底要交出什么。

多个 agent 各自返回一段漂亮的 prose，并不等于获得了多份独立证据。研究、实现和验证角色应共享最小的输出结构，例如事实、证据位置、结论、不确定点和建议动作。汇总阶段才有可能比较分歧，而不是把几段自然语言拼成会议纪要。对迁移、批量检查和代码库调研而言，结构化交接往往比增加并行数更重要。

## 验证角色需要看到证据，也需要被限制

迁移和重构适合把调用点、模块和失败测试分片处理，再由独立角色检查旧路径是否残留。深度研究适合并行检索、追源、核验 claims 和合成报告。根因调查则可以让不同角色分别查看日志、代码、数据和历史变更，再让 verifier 与 refuter 挑战假设。

但 verifier 不能被当作自动真理机。它应明确检查范围、使用的 rubric 和未覆盖的风险；验证通过只说明给定检查通过。每个额外角色还会消耗预算，因此验证应该放在错误后果高、人工复查昂贵的地方，而不是给所有小任务加上一层仪式。

外部输入还要求权限隔离。读取公开 issue、Slack 事件或用户材料的 agent，不应直接执行高权限动作；triage 角色先分类和升级，行动角色只接受筛选后的结构化信息。worktree 隔离文件修改，quarantine 隔离不可信输入，两者解决的是不同问题。

## 动态生成不等于自动定义目标

workflow 可以生成角色，却不能替任务补上成功标准。像“让产品变好”“把仓库整理一下”这样的请求，若先并行启动一组 agent，只会得到许多格式整齐但无法验收的建议。先写清楚目标、rubric 和失败边界，再决定是否动态编排，往往更省计算。

同样的原则适用于重复运行。周期性工作需要判断“没有新发现”是否足以停止；研究需要判断来源是否已经覆盖；迁移需要判断旧接口是否彻底消失。预算、连续无进展轮数和人工接管条件，都应该成为 workflow 的一部分，而不是运行失控后的补丁。

## 保存要等结构证明自己

动态 workflow 可以保存到工作流目录，也可以通过 skill 分发。这个能力适合已经在多个相近任务中表现稳定的结构。一次成功运行不代表角色划分、输出格式和停止条件都值得长期复用；它可能只是碰巧遇到了简单输入。

保存前应检查：子 agent 是否按格式返回，汇总能否处理冲突，中断后是否能恢复，预算是否可控，拥有外部输入的角色是否权限过大。skill 提供稳定的项目知识和脚本，workflow 决定这次如何组合它们。前者和后者可以互补，但一次性脚手架不应过早变成团队规则。

如果下一次任务还需要重新解释每个角色如何交接，就先别急着把这个 workflow 保存成默认流程。把一次分歧处理清楚，比多存一个看起来完整的模板更有用。

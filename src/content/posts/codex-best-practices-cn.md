Codex 最容易让人误判的地方，是它经常能在信息不完整时给出一份像样的结果。结果越像样，越容易把问题归咎于提示词不够漂亮；但在真实仓库里，决定返工的通常不是措辞，而是任务有没有边界。文件在哪里、哪些约束有效、什么算完成、哪些动作不能碰，这些信息缺一块，agent 就会用默认假设补上。

这让我更在意一个容易被忽略的成本：为了让 agent 开始得快，省下的解释会不会在审查时成倍补回来？任务边界、仓库规则和验证方式，都值得沿着这个问题重新看一遍。

## 任务边界比提示词修辞重要

“修复登录问题”是一句自然语言，却不是一个可交付任务。它没有指定搜索范围，也没有说明错误边界，更没有给出完成证据。OpenAI 建议在请求里同时交代目标、上下文、约束和完成标准，价值正在这里：这四项不是提示词模板，而是把猜测从 agent 身上拿回来。

例如，说明相关文件、现有错误类型、不可改变的架构和需要覆盖的测试分支，实际是在规定 agent 可以做哪些假设。一个请求即使只有两句话，只要把这些边界交代清楚，也可能比一段充满礼貌和背景的长提示更可靠。推理强度同理：简单的单文件改动和跨模块调试需要不同的分析投入，把所有任务都推到最高档只是增加等待，把复杂问题当成快问快答则是把风险留到 diff 里。

计划的作用也不在于产生一份漂亮文档，而在于暴露不确定性。复杂任务先读仓库、找现有模式、写出方案和验收条件，至少让“理解错了什么”在实现前有机会被发现。若连完成标准都说不清，直接让 agent 改代码，只是把模糊问题延后到审查阶段。

因此，`/plan` 或 `PLANS.md` 的核心价值不是某个产品功能，而是 checkpoint：上下文膨胀时可以换线程继续，方案争议时有东西可对照，执行失败时能区分研究不足、路径错误和验收过松。计划保存意图，却不替人授权；涉及不可逆操作时，关键假设仍然需要人工确认。

## 持久规则有用，也会腐化

把稳定规则放进 `AGENTS.md`，是对“每次都在聊天里重复提醒”这件事的正确反应。仓库结构、测试命令、代码风格、安全限制和完成定义都适合成为持久上下文。它们让 agent 在进入具体文件之前就知道哪些选择不合规。

但规则文件不是记忆保险箱。写进去的每一条规则都要靠日常维护，否则它会从约束变成噪声：命令可能过时，目录可能移动，过去的例外可能被误当成普遍原则。规则越长，越需要有人判断它是否仍然影响决策。稳定制度应该短、具体、可执行；一次性的背景和未经验证的偏好留在任务里更诚实。

这也改变了复盘方式。同类错误再次出现时，不能只说“agent 没遵守规则”，还要检查规则是否写成了可验证的动作。比如“注意安全”无法指导修改，“不要访问生产环境，完成后运行某个检查”才有明确边界。规则的价值不在于表达立场，而在于能否改变下一次决策。

MCP、Skill 和 Automation 其实是同一个问题的不同阶段。MCP 适合连接仓库外且会变化的信息；Skill 适合封装输入、输出和验证都已稳定的重复方法；Automation 只应接管已经足够可预测的流程。工具接得越多不一定越强，未稳定的方法越早自动化，错误就越快被复制。

## 自动化速度必须支付验证成本

Codex 可以搜索、编辑、跑命令，甚至按要求做 review；但“自己验证”不等于“不需要人验证”。测试、类型检查、格式检查、行为确认和 diff 审查，分别回答不同问题：代码能不能运行，接口是否一致，改动是否符合需求，以及是否偷偷扩大了范围。把这些步骤合并成一句“确认没问题”，只是在隐藏成本。

验证也不是越多越好。低风险单文件改动可能只需要相关测试和 diff；跨模块重构则需要更完整的检查。关键是把验证和风险绑定，而不是把它当作发布前的仪式。`/review` 可以帮助发现遗漏和无关修改，却不能代替真实测试；静态审查发现可能的问题，执行结果才提供行为证据。

权限取舍同样要算进验证成本。减少确认弹窗能提高吞吐，但不会提高判断质量；一旦 agent 可以改文件、调用外部服务或使用登录态，错误也会更快落地。放宽权限的前提应该是工作目录清楚、git 可回退、危险动作有明确授权，并且验收步骤不会因为追求速度而被删掉。

所以人的位置不是消失，而是从逐行监工变成设定风险等级、检查关键假设和阅读证据。agent 负责扩大执行量，人负责决定什么证据足够、什么失败必须停下。

## 并行吞吐受审查能力限制

多个线程、subagent、fork 和远程会话可以提高吞吐，但前提是每条任务线都有独立输入、输出和交接点。一个线程适合承载连贯问题；方向真正分叉时再 fork，才不会让不同目标互相污染。多个线程同时改同一批文件，却没有 worktree 或其他隔离方式，得到的往往是难以归因的冲突。

并行还有一个常被忽略的上限：人能否审查结果。让三个 agent 同时产出三个方案，生成速度确实更快，但如果没有足够时间比较差异、运行检查和追问假设，输出只是堆积。Claude 与 Codex 的分工也应按“研究、实现、复核”等职责拆开，而不是简单增加模型数量；分工只有带着交接标准，才会形成接力。

这使得“更快”不再是单一指标。真正可持续的速度，是计划让上下文可恢复，规则让决策可重复，验证让结果可相信，并行让独立工作彼此隔离。任何一项缺失，吞吐量都会以返工、冲突或无法追责的错误形式收回来。

如果三个任务已经产出、却没有一份结果被认真检查，此时更合理的动作是停止开新线程，先把一个结果验收完。能持续交付多少，应该按这个速度来算。

一个长调试任务可能已经排除了缓存问题，也确认失败只出现在特定输入上。换过一次上下文，Agent 却重新建议清缓存，接着又跑一遍做过的检查。代码还在，日志也还在，丢掉的是“哪些路已经走不通”的工作状态。

这种失败很容易被归结为记性不好。但继续扩大窗口只能推迟问题：任务迟早要跨过窗口边界，关键是下一段执行凭什么接上前面的判断。

Codex 的 token budget、`new_context` 和 history/notes 提供了一条值得拆开的路径。它把剩余容量变成模型能参考的信息，允许主动换窗口，再通过历史和笔记恢复工作。不过，理解这套机制前，需要先把“实现了什么”和“所有用户已经用上什么”分开。

## 变化发生在一条有条件启用的路径上

截至 2026 年 9 月 4 日的 [Codex 代码快照](https://github.com/openai/codex/tree/47b0f7d540e9abf932e9b518ab306e389744998e)，`token_budget` 和 `context_management` 都标为开发中，静态默认值为关闭。另一方面，运行时确实允许模型元数据提供启用默认值，但会检查显式配置及管理策略；history/notes 扩展还依赖对应配置、provider 和认证条件。[功能声明](https://github.com/openai/codex/blob/47b0f7d540e9abf932e9b518ab306e389744998e/codex-rs/features/src/lib.rs#L1587)、[启用逻辑](https://github.com/openai/codex/blob/47b0f7d540e9abf932e9b518ab306e389744998e/codex-rs/core/src/session/token_budget.rs)。

因此，“Codex 已经全面放弃 compaction”超出了这些证据。默认值关闭，也不能反过来推导出任何用户都无法使用；实际行为还要看运行时提供的模型信息和配置。

更准确的变化是：在 token budget 路径下，切换窗口可以跳过模型或服务端的摘要过程，但仍沿用 compaction 的生命周期，包括相关 hooks 和事件。源码甚至把这段实现放在 `compact_token_budget.rs` 中。它替换了特定路径上的状态交接方式，并没有从系统里删掉“压缩”这个概念。[切换实现](https://github.com/openai/codex/blob/47b0f7d540e9abf932e9b518ab306e389744998e/codex-rs/core/src/compact_token_budget.rs)。

## 窗口容量开始参与下一步决策

如果模型只能看到任务，却不知道窗口快满了，就可能在最不合适的时候展开一次大搜索：工具返回大量日志，下一步还没来得及解释，系统就必须处理上下文容量。

预算信息的作用，是让执行顺序可以改变。剩余空间充足时继续调查；空间紧张时，先保存结论、未决问题和证据位置，再换窗口。这里说的是当前窗口的可用空间，不是账户用量，也不是整个任务还能花多少费用。

主动切换也需要兜底。上述版本提供了接近边界时的提醒，以及可配置的后备提示和缓冲空间；测试还覆盖了模型没有及时调用 `new_context`、最终耗尽缓冲后自动换窗口的情况。把容量告诉模型，是给它安排工作的机会；真正限制执行的仍然是程序。[预算与切换测试](https://github.com/openai/codex/blob/47b0f7d540e9abf932e9b518ab306e389744998e/codex-rs/core/tests/suite/token_budget.rs)。

这也是做自己的 Agent 时应保留的区别：“请在窗口满前整理进度”是一条行为要求，容量检测和后备分支才是防止越界的机制。前者可能被忽略，后者不能缺席。

## 换窗口以后，历史和笔记承担不同工作

`new_context` 的工具定义明确区分了上下文和环境：启动新窗口不会清空环境状态。已经修改的文件不会因此回滚，正在讨论的内容却未必继续留在下一次模型输入里。[工具定义](https://github.com/openai/codex/blob/47b0f7d540e9abf932e9b518ab306e389744998e/codex-rs/core/src/tools/handlers/new_context_window_spec.rs)。

只实现这一步，Agent 仍可能在同一个仓库里从头调查。history 和 notes 的配合才解决了后半个问题：前者用于查找过去的窗口和条目，后者用于保存模型整理的工作笔记。它们是恢复执行状态的工具，不能仅凭名称就等同于面向所有后续任务的长期用户记忆。[历史与笔记接口](https://github.com/openai/codex/blob/47b0f7d540e9abf932e9b518ab306e389744998e/codex-rs/ext/history-notes/src/tools.rs)。

| 状态放在哪里 | 适合保留什么 | 容易出现的失败 |
| --- | --- | --- |
| 当前上下文 | 正在分析的代码、最近的工具结果 | 内容过多，挤占下一步推理空间 |
| 工作笔记 | 当前结论、未完成动作、证据位置 | 把推测写成事实，把旧进度带到新阶段 |
| 可检索历史 | 当时的请求、执行记录及细节 | 记录存在，却没有被正确检索出来 |

这些角色有分工，才不必把所有旧内容重新塞回窗口。恢复时先看工作状态，需要追问某个判断时再取证据；如果一换窗口就回读全部历史，很快又会遇到相同的容量问题。

笔记也不该只写“已调查登录失败”。一份能接力的状态至少要说明：失败在哪个输入上复现，哪些解释已经被证据排除，改了哪些文件，哪项验证尚未完成。比如“已修改错误处理，单元测试通过，但集成测试尚未运行”，比“登录问题基本修好”多不了多少字，却不会把下一段执行直接引向交付。

## 保留原始记录，仍然会损失有效信息

不在切换时生成摘要，减少了一次集中概括的机会，但没有消除筛选。模型仍要决定写什么笔记、使用什么查询、读哪些片段。检索没有命中，或者命中了错误时间点的记录，效果上依然可能像失忆。

这里有个具体限制：该版本 history/notes 的内容搜索按区分大小写的字面子串匹配。笔记只留下“鉴权异常”，而历史中的关键线索是一个英文错误码，就未必能靠同一个查询找回来。保存错误码、文件名和记录定位信息，往往比把问题概括得流畅更有用。

反过来，压缩也不必意味着原始记录从存储中被删除。缩小模型输入，与是否保留可检索档案，是两个可以分别设计的决定。摘要可以保留近期状态，历史可以承担按需取证；有了历史，也仍然需要一份简短、可靠的工作入口。

两种方式的代价应放到同一项任务里比较：压缩可能遗漏细节，按需恢复会增加检索和读取成本。若省下的摘要调用换来了十次无效搜索，窗口变轻了，任务未必更快。

## 验收要看切换后的第一步

验证这种机制，不能只检查窗口 ID 变了，或者旧消息不再出现在请求中。代码测试可以证明这些转换符合预期，却不能单独证明模型成功接回了业务任务。

一个更有区分度的场景，是在切换前留下三类状态：已经排除的错误方向、明确禁止执行的动作、还有一个尚未完成的检查。切换后观察 Agent 是否重走旧路、是否保留限制、是否从那项检查继续。再故意让笔记遗漏一个参数，看它能否回查记录，而不是猜出一个合理值。

评估时还应记录恢复需要多少次工具调用、读回多少内容、有没有把过期结论当成当前事实。这些结果比“支持多少窗口”更接近长期协作的成本。

上下文切换真正要守住的，是执行中的证据关系：这个结论为什么成立，这个动作为什么还不能做，下一步为什么轮到这里。新窗口打开以后，Agent 如果知道从哪条未完成的验证继续，前一段工作才算被保留下来。

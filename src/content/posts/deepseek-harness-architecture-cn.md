给一个正在运行的 Agent 增加工具，通常不难。难的是后来把它换掉：旧监听器还在接收事件，定时器还在写日志，新旧实现同时处理请求。界面上只有一个插件，进程里却留下了两套行为。

如果 Agent 还能生成插件并装进自己的运行环境，这个问题会更明显。第一次加载成功只能证明入口可用，卸载、重载和初始化失败之后能否恢复，才决定这套扩展机制能不能长期使用。

DeepSeek Harness 把模型适配器、工具注册、会话日志和 Agent Loop 都做成 Cordis 插件。它值得细看的地方，是把“这项能力由谁提供”和“它留下的资源由谁收回”放进了同一套运行机制。[架构文档](https://github.com/deepseek-ai/deepseek-harness/blob/8505d61f6965e95f330f09828bb420479891d9b3/docs/architecture.zh.md)中的插件树，也因此不仅是启动清单，还是运行状态的组织方式。

## 加载时就写好退出路径

Cordis 为每个插件实例保留 Fiber，管理等待依赖、加载、活动和卸载等状态。插件需要的服务尚未出现时，可以等待；初始化抛错，也有对应的失败状态。业务代码不用到处写轮询，猜测其他模块是否已经准备好。

资源清理由 effect 管理。通过框架注册的监听器、子插件和服务，会关联到所属插件的生命周期；框架之外创建的定时器、连接或文件监听，则需要放进 `ctx.effect()`，返回释放资源的函数。[生命周期教程](https://github.com/deepseek-ai/deepseek-harness/blob/8505d61f6965e95f330f09828bb420479891d9b3/docs/cordis-tutorial/02-lifecycle-and-effects.zh.md)对此给了明确约定。

创建与清理写在一起，减少的是维护上的遗漏。例如为会话启动一个定期刷盘任务，注册时就说明怎样停止它，插件退出时由框架调用这段逻辑。以后调整刷新频率，不必再去另一个文件寻找销毁钩子。

这里有个容易被“逆序撤销”掩盖的细节：disposer 按注册的逆序启动，多个异步 disposer 可以并发运行。若必须先停止生产数据，再等待缓冲写完，最后关闭连接，就应当把这些步骤放在一个清理函数里依次 `await`。逆序启动不等于前一个清理已经完成。

更不能把卸载理解成撤回所有业务结果。注销监听器可以阻止未来处理事件，已经发出去的通知却不会因此消失；释放数据库连接，也不会自动回滚之前提交的事务。

验证插件时，值得加一个很小的场景：加载、卸载、再加载，发送同一条事件，观察它是否只被处理一次。接着让初始化在中途失败，再检查连接数和监听器数量。比起只确认“工具出现了”，这更接近插件实际要承担的责任。

## 一份预设复用，状态仍要分开

另一个问题来自多会话。十个会话使用同一种编码预设，若每个都完整挂载一遍插件树，文件监听、提示词注册和相关资源也可能重复十份。

DSH 的 [Agent Preset](https://github.com/deepseek-ai/deepseek-harness/blob/8505d61f6965e95f330f09828bb420479891d9b3/packages/preset/agent-presets/README.md)把一份预设挂载为可共享的实例，再让会话通过作用域关系加入。工具与提示词按 `agent → preset → global` 查找，较近的定义遮蔽较远的定义。预设提供共同能力，会话仍可以有自己的覆盖。

这省掉的是重复装配，不是状态隔离的工作。共享插件如果只保存一个 `currentTask`，后进入的会话仍可能覆盖前一个会话。需要按 Session 或 Agent 保存的数据，必须使用对应身份作为索引。

一个实用验证是同时开启两个会话：A 写入自己的待办，B 更新另一份待办，再分别恢复读取。两边都能调用同一工具，并不能证明两边拿到的是自己的状态。共享实例带来的资源收益，只有在这一步通过后才成立。

作用域也需要与权限分开理解。让一个会话看不到某个工具，可以减少误用入口；如果它仍能通过 shell 访问相同资源，实际权限并没有随之收回。注册表决定能力如何呈现，执行环境决定动作能走到哪里。

## 编排变成代码，检查仍要逐次发生

普通工具调用常常需要多轮往返：查目录、读取几个文件、筛选结果，然后再决定下一步。对其中已经明确的循环和条件判断，让模型写一段程序执行，可以减少中间数据反复进入上下文的成本。

DSH 的 Code Mode 正是在这层改变工具使用方式。需要关注的不是代码能否一次调用十个工具，而是这十次调用是否仍走正常检查。

[工具执行流水线](https://github.com/deepseek-ai/deepseek-harness/blob/8505d61f6965e95f330f09828bb420479891d9b3/docs/tool-execution-pipeline.zh.md)把前置处理、守卫、执行、后置处理和最终结果分开；Code Mode 的子调用也经过这条链路。否则外层 `run_code` 获准一次，就可能把内部本该分别检查的动作全部放行。

但工具管线与代码隔离仍是两件事。[Worker Thread 后端](https://github.com/deepseek-ai/deepseek-harness/blob/8505d61f6965e95f330f09828bb420479891d9b3/packages/code-runtime/code-runtime-worker-thread/README.md)为每次运行建立新的 Worker，设置资源预算并支持终止，同时明确说明它不构成安全边界。结束 Worker 也不保证清理代码另外启动的操作系统进程。

因此，下面几项不能混成一个“已隔离”的结论：

| 机制 | 主要解决什么 | 还需要单独处理什么 |
| --- | --- | --- |
| 每次新建 Worker | 减少运行之间的内存状态残留 | 文件、网络和派生进程的影响 |
| 时间与内存预算 | 限制失控计算占用资源 | 业务动作的授权范围 |
| 工具调用流水线 | 对注册工具执行统一检查 | 绕过工具接口的直接访问 |
| 外部执行环境 | 限定进程实际能访问的资源 | 输出是否满足任务要求 |

架构评审时，应当拿一次被拒绝的内部调用做验证：它是否真的没有执行，错误是否传回程序，模型最后看到的结果是否保留了拒绝原因。只看外层调用成功，会漏掉最关键的一段。

## 日志保留事实，恢复仍有条件

运行时可以替换组件之后，还需要回答：这次行为究竟发生在什么配置、什么上下文里？只保存最终回答，很难定位是模型判断失误、工具拒绝，还是插件改写了结果。

DSH 的 [Session](https://github.com/deepseek-ai/deepseek-harness/blob/8505d61f6965e95f330f09828bb420479891d9b3/packages/core/session/README.md)以追加事件记录交互历史，模型消息由日志投影得到。会话核心与持久化实现分开，内存里已经产生事件，与事件已经落盘，也因此需要分别判断。

这给调试提供了一条清晰路径：先确认模型看见了什么，再确认它发起什么调用，最后对照实际返回。若界面展示、恢复后的上下文和持久化记录各讲一套故事，就该检查投影或写入链路。

日志能重建历史，并不意味着再次执行会得到相同结果。远程接口会变化，文件可能被其他进程修改，重复提交也可能产生第二次副作用。回放观察与重新执行，需要在产品交互上明确区分。

对这种架构，最有价值的验收常发生在“做完”之后：卸载是否留下活资源，恢复是否丢失已接收输入，被拒绝的动作有没有真的停住。插件越容易拼装，越需要把这些边界测清楚。否则新增能力的速度，最终会变成排查残留状态的速度。

一个 Agent 查完数据库，工具返回了结果，但模型还没有向用户解释。这时工具执行结束了，任务却未必结束。反过来，模型已经输出最后一句话，用户刚刚发来的补充要求还在队列里，也不能直接把整个运行实例停掉。

用 `while (hasToolCalls)` 理解 Agent Loop，最容易漏掉的就是这些时刻：同样是“结束”，究竟结束了什么，谁还有权让它继续？

下面按运行层次拆开这个问题。代码固定在 [DeepSeek Harness 的 dsh-v0.1.2-alpha.1](https://github.com/deepseek-ai/deepseek-harness/tree/cd5ef8148158c3a752a658978873241fdf8e2bbc) 和 [Pi 的 853a80d2](https://github.com/badlogic/pi-mono/tree/853a80d26c90a14c1886f0ebb8ffaae133ca2185)，这里的 Pi 指 `pi-agent-core` 中的 Agent Loop。版本固定下来，是为了避免把后续改动混进同一套判断。

## 五层边界

DeepSeek Harness 里，至少有五种值得分开的结束。

| 层次 | 结束意味着什么 | 还不能说明什么 |
| --- | --- | --- |
| 模型请求 | 本次模型流已经停止 | 工具是否执行、用户诉求是否完成 |
| step | 当前模型响应及其工具批次处理完毕 | 是否还需要模型读取工具结果 |
| turn | 当前轮没有默认续跑需求，也没有待处理的 next-step 输入 | 下一轮是否还有普通消息 |
| driver activity | 当前驱动不再继续处理 turn，进入 idle | 长期目标是否完成 |
| 长期工作流 | Goal 或其他工作流达到自己的结束状态 | 不能仅靠一次模型停止推断 |

一个 turn 可以包含“模型调用—工具执行—模型回访”的多次往返。普通工具返回以后，通常还需要模型解释结果，所以 step 关闭不等于 turn 关闭。正常收敛时，还要检查当前轮的输入队列；错误、阻断与取消则走各自的退出路径。

Pi 的术语粒度不同。一次 assistant 响应及对应工具批次构成一轮，随后发出 `turn_end`；再次请求模型，就进入下一轮。一次 Agent Loop 调用退出时发出 `agent_end`。

因此，DeepSeek 的 step 更接近 Pi 的 turn，DeepSeek 的 driver activity 更接近 Pi 的一次循环调用。比较日志时，直接拿两边的 turn 数衡量推理深度，会差一层。

## 驱动收敛

DeepSeek 的驱动入口很短：反复等待 `turn()`，直到它不再要求继续。但驱动能不能真正停稳，还取决于 `idle`、`maintenance` 和 `running` 三种内部状态。

运行状态保存当前 turn、step、取消控制器，以及 `wakeRequested`。维护期间也保留取消和唤醒信息。这解决的是一个具体竞态：维护尚未结束，新输入已经到达。此时既不能重复启动驱动，也不能把这次唤醒丢掉。

取消期间收到的新输入同样需要重新归属。旧 activity 已经被取消，新消息就应进入后续 turn，而不是继续塞给正在退出的运行。输入归类需要基于稳定的取消状态，避免同步观察者的重入改变判断。

`whenIdle()` 也不只是等待手里那一个 Promise。等待结束后，它还会检查当前 activity 是否已经换成了新的；换了，就继续等。否则调用方等到的可能只是“上一轮停了”，实际下一轮早已启动。

即便如此，idle 仍然只是当前时刻的运行状态。一个后来到达的请求，当然还可以重新唤醒它。

## Turn 状态机

DeepSeek 在领取输入前就记录 `turn/start`，然后为退出路径写入对应的 `turn/end`。这使“尚未发起模型请求就被阻断”和“模型正常回答完毕”都能留下完整边界。

第一步领取 next-turn 输入，后续步骤领取 next-step 输入。中间依次完成上下文装配、pre-step 钩子、step 开始、模型与工具处理，再决定是否进入下一步。pre-step 拒绝时，可以在没有调用模型的情况下结束；初始输入为空，也可能直接正常关闭。

理解这段状态机，需要盯住 step 的三类正常返回值：

- `completed`：当前 step 不再要求自动回访模型。
- `max-tokens`：本次生成触及上限，需要保留截断事实。
- `null`：工具结果仍需模型处理，应继续运行。

这里的 `null` 有明确含义，并非“运行结果未知”。把它理解成尚未完成的模型回访，会比把所有分支都压成一个 `done` 更容易读懂。

## 停止钩子

DeepSeek 的 `agent/turn-stopping` 并不靠一个布尔返回值决定继续。

当 turn 已具备结束条件，且 next-step 队列为空时，运行时先调用停止钩子。钩子执行后，再检查一次队列。插件若希望继续，就提交实际的下一步输入；队列仍为空，才关闭当前 turn。[停止前的队列复查](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef8148158c3a752a658978873241fdf8e2bbc/packages/core/agent-loop/src/agent.ts#L292-L307)

这样做的好处是，继续运行必须有内容承接。插件不能只说“先别停”，还要说明下一步处理什么。多个插件也不必再争论各自返回的 true、false 应该怎样合并。

代价是，插件作者需要理解输入属于当前 step 之后，还是下一 turn。继续执行的权限被放进了消息与队列规则里，这部分约定必须清楚。

## Step 债务

普通工具调用会产生一次模型回访需求：工具已经给出结果，模型还需要据此继续回答。

DeepSeek 的处理顺序是先检查生成状态，再决定是否执行工具。触及 `max-tokens` 时直接返回，不进入工具批次；没有工具时正常完成；有工具时执行批次，再根据工具是否要求收口决定是否回访。[step 的出口](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef8148158c3a752a658978873241fdf8e2bbc/packages/core/agent-loop/src/agent.ts#L426-L434)

这个顺序很有必要。被截断的工具参数，即使勉强能解析成 JSON，也不代表语义完整。尤其是写入操作，不能用“语法合法”替代“参数生成完整”。

Pi 对这类情况采取另一条路径：当 `length` 响应带有工具调用时，为这些调用生成失败结果，并保留继续运行的条件，让模型有机会处理失败，而不是执行截断的调用。[Pi 的截断处理](https://github.com/badlogic/pi-mono/blob/853a80d26c90a14c1886f0ebb8ffaae133ca2185/packages/agent/src/agent-loop.ts#L225-L235)

两者都在工具执行前挡住这次截断，区别在于失败怎样进入后续控制流。不能把 Pi 的 `length` 一概解释成整次 Agent 调用立即结束，也不能把 DeepSeek 的 `max-tokens` 理解成长期目标已完成。

## 粘性结果

假设一个 step 触及 token 上限，但停止钩子又补入上下文，后续 step 正常输出了文字。整个 turn 应该记作正常完成，还是保留之前的截断？

DeepSeek 选择保留。`turnEnds` 一旦记录了 `max-tokens`，后续正常 step 的结果不会把它降回 `completed`。不过错误、取消和阻断有独立分支，不能把这条规则扩大成任何退出情况下都绝不改变。[结果保留逻辑](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef8148158c3a752a658978873241fdf8e2bbc/packages/core/agent-loop/src/agent.ts#L292-L297)

这对监控很有价值。最后一条消息看起来完整，不代表整轮没有经历过资源限制。如果统计只保留最后一步的状态，很多异常会被一段正常收尾遮住。

更一般的设计判断是：最终状态和过程事实最好分开保存。最终状态决定接下来怎么调度，过程事实用于解释这一次究竟发生过什么。

## 工具收口

DeepSeek 的 `concludesTurn` 与 Pi 的 `terminate` 看起来相近，聚合方式却不同。

| 实现 | 批次判断 | 对自动回访的影响 |
| --- | --- | --- |
| DeepSeek | 已提交结果中任意一个 `concludesTurn` 为真 | 当前 step 可以不再自动回访模型 |
| Pi | 非空结果集中的每个 `terminate` 都为真 | 当前工具批次不再要求自动回访模型 |

DeepSeek 使用 OR，Pi 使用 AND。[DeepSeek 的聚合](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef8148158c3a752a658978873241fdf8e2bbc/packages/core/agent-loop/src/tool-calls.ts#L147-L159)、[Pi 的聚合](https://github.com/badlogic/pi-mono/blob/853a80d26c90a14c1886f0ebb8ffaae133ca2185/packages/agent/src/agent-loop.ts#L580-L582)

但两者都不能直接翻译成“现在杀掉整个循环”。DeepSeek 不会因为一个工具要求收口就中断当前批次，工具提交的 `additionalContexts` 仍会进入 next-step；Pi 消除了工具续跑条件以后，steering 或 follow-up 也仍可能带来下一轮。

这里暴露的是工具契约的差异。一个批次同时包含“提交结果”和“获取还需解释的数据”，在 OR 语义下，提交工具的结束标记可能撤销整批默认回访需求。设计工具时，要明确谁有权作出这个决定；不能把一个局部动作完成，随手标成整个 turn 可以结束。

## 顺序提交

并行工具的完成顺序通常不稳定。先发出的慢查询可能最后返回，后发出的缓存查询反而先结束。

DeepSeek 用 slots 暂存结果，再沿着输入顺序推进提交位置。后面的工具即使先完成，也要等前面可提交后，才把结果依次交给上下文和事件消费者。Pi 的并行结果汇总也保留输入顺序。

稳定提交顺序有利于重放和调试：同一批工具不必因为网络时序不同，就呈现出不同的结果排列。但它也带来等待，排在前面的慢工具会挡住后续结果的提交。

更容易误解的是外部副作用。日志按顺序提交，不代表数据库写入也按这个顺序发生。两个工具已经并发执行，后端谁先落库仍由实际执行决定。需要严格先后关系的动作，应由调度或业务事务保证。

DeepSeek 的调度还会在补充任务时重新读取执行模式。若转入排他执行，需要等在途任务排空再继续。这约束后续派发，不能撤销已经启动的并发调用。

## 取消语义

用户点击停止，至少涉及两类工具：尚未启动的，以及已经启动的。

DeepSeek 停止派发新工具，等待已启动任务收敛；对派发前被取消的调用，可以写入对应的取消结果，避免对话记录留下没有解释的工具调用。已启动工具的返回与附加上下文，仍需要按提交规则处理。

如果发生的是调度器自身失败，则应停止新增派发、等待在途任务，再传播失败，不能替尚未执行的动作编造业务结果。

Pi 也通过取消信号影响工具执行，但取消能否及时生效，取决于工具有没有响应信号。请求已经发往外部系统，停止本地等待不会自动撤销远端写入。

所以，取消只是运行控制的一部分。涉及提交、付款或发信时，还需要幂等键、结果查询或补偿机制，才能回答用户最关心的那句：刚才到底有没有执行成功。

## 原因体系

DeepSeek 为 turn 提供了更细的结束原因。

| 原因 | 应怎样理解 |
| --- | --- |
| `completed` | 正常收敛，可能是文本完成、工具收口或空输入 |
| `blocked` | 被 pre-step 等条件阻断，没有继续推进 |
| `max-tokens` | 本轮保留了生成截断的事实 |
| `aborted` | 运行受到取消信号影响而退出 |
| `error` | 模型或其他运行错误导致退出 |
| `interrupted` | 恢复时发现此前未闭合的 turn，为它补记中断 |

`interrupted` 尤其值得单独留着。进程消失时，没有机会执行正常取消流程；恢复后补上的中断记录，应与用户主动停止区分。

Pi 的 assistant `stopReason`，如 `stop`、`length`、`toolUse`、`error`、`aborted`，更接近模型响应层。它们与 DeepSeek 的 turn 结束原因覆盖范围不同。

同样，`completed` 只能证明这一层正常结束。业务验收是否通过，需要业务自己的证据。

## Goal 外循环

DeepSeek 的 Goal Driver 位于普通驱动之外。Agent 进入 idle 后，它检查目标状态、当前实例是否仍有效、有无普通待处理输入、自动推进是否启用，以及轮次预算，再决定是否注入下一轮消息。

这里最重要的是分开持久状态和本次进程的推进授权。

Goal 可以持久保存为 `active`，但自动执行还需要当前 activation 处于 armed 状态。恢复或 fork 后，看见一个 active 目标，并不意味着新进程就可以无条件继续操作。

达到轮次限制时，目标会进入相应的阻断状态；遇到 `max-tokens`、错误或持久化失败等情况，自动推进会被解除。取消也需要相应地暂停或解除推进，避免 Agent 刚停下来，又被 idle 监听器立即启动。

长期任务真正危险的地方，往往是这些“看起来还没完成，所以继续”的默认行为。恢复数据和恢复执行权限，应该是两个明确动作。

## Goal 收尾

目标被标为 complete 或 blocked 后，用户还需要收到说明。DeepSeek 把这两件事分开：先保存 Goal 状态，再把收尾上下文送入 next-step，让模型解释结果。

因此，Goal 已经完成，当前 turn 仍可能再运行一个 step。这并不矛盾，后一步承担的是交代结果。

先保存状态有一个直接收益：即使最后的说明生成失败，也不至于因为“没来得及说完成”而重复推进目标。当然，界面也要有能力区分目标已经完成与最后一条消息发送失败，否则后端正确，用户仍然会误判。

## Pi 双循环

Pi 的主控制流相对集中。内层处理工具回访与 steering，内层准备退出后，外层再读取 follow-up；如果还有后续消息，就再进入内层。

三个回调承担了主要扩展点：

- `getSteeringMessages`：把新输入带入下一次模型处理。
- `getFollowUpMessages`：在当前工作准备收敛时，提供后续任务。
- `shouldStopAfterTurn`：当前轮完成后，决定是否直接退出本次调用。

最后一个回调有更高的退出优先级。模型响应、工具批次和 `turn_end` 处理完后，若它返回 true，Pi 直接发出 `agent_end` 并返回，不再读取下一批 steering 或 follow-up。[Pi 的退出顺序](https://github.com/badlogic/pi-mono/blob/853a80d26c90a14c1886f0ebb8ffaae133ca2185/packages/agent/src/agent-loop.ts#L241-L274)

这与 DeepSeek“停止钩子执行后再复查 inbox”的方式不同。接入宿主时，需要确定未消费的消息由谁保留、何时再次启动。

另外，这个 Pi 版本的 steering 不会跳过当前 assistant 响应剩余的工具调用。它是在本批工具处理后进入下一轮，不能把插话机制当成工具撤销机制。[steering 的接口约定](https://github.com/badlogic/pi-mono/blob/853a80d26c90a14c1886f0ebb8ffaae133ca2185/packages/agent/src/types.ts#L235-L245)

## 失败路径

Pi 收到 `error` 或 `aborted` 的 assistant 响应时，会关闭当前轮并退出本次调用。这与正常输出后继续读取队列的路径不同。

DeepSeek 在请求失败处提供错误处理钩子，可以按处理结果重试。同一个逻辑 step 可能重新创建输出组装器、发起另一次模型请求，而 turn 和 step 的身份保持不变。

因此，一个 step 不一定只对应一次真实请求。统计成本时，要看请求 attempt；统计对话结构时，要看 step；判断任务是否完成，则还要看更外层状态。把这些计数合并，很容易得到“轮数没变，成本却翻倍”的困惑。

重试还应按失败位置区分。模型流失败后的重试，不能直接推广成有副作用工具失败后的盲目重放。后者必须先确认上一次动作是否已经落地。

## 请求序列

DeepSeek 还为模型、推理强度、token 上限、系统提示词和工具定义等请求配置维护序列边界。

这层机制与结束判断的关系在于：运行虽然还在继续，下一次请求采用的契约可能已经改变。恢复、显式开启新序列或请求配置变化，都需要让日志能辨认这种边界；Goal 轮次也可以开启新的请求序列。

如果只记录消息正文，后来很难解释两轮相似输入为什么表现不同。真正改变行为的，可能是工具集合、系统提示词或模型配置。

请求序列本身不是停止条件。它记录的是接下来在什么配置下继续。配置快照还需要稳定的规范化方式，否则字段排列变化也可能制造没有意义的新边界。

## 日志消费

前端和监控系统应先明确问题，再选事件。

| 想知道什么 | 应观察什么 |
| --- | --- |
| 模型这次是否输出完 | 响应结束状态、usage |
| 当前 turn 是否关闭 | `turn/start` 与 `turn/end` |
| 当前驱动是否空闲 | 状态变化或 `whenIdle()` |
| 长期目标是否结束 | Goal 的持久状态 |
| Plan mode 是否已经退出 | 实际生效的模式状态 |
| 是否还可能再被唤醒 | 实例生命周期及外部调度状态 |

例如，看见 `exit_plan_mode` 工具调用，不能立刻认定模式已经切换。意图、审批与实际生效之间，可能还隔着一个处理步骤。

Pi 的 `agent_end` 也只描述这次调用结束。宿主之后仍可发起新调用，外部 Goal 调度器也可能继续工作。一个事件能证明的范围，应与生成它的那一层保持一致。

## 工程取舍

DeepSeek 把 phase、inbox、唤醒标记、事件日志、恢复和 Goal 推进纳入运行时，获得的是跨轮运行的一致约定。代价则是插件接入者需要理解更多状态与边界。

Pi 把核心循环集中在一次调用里，通过回调让宿主补充行为。控制流更容易顺着读下来，但持久目标、恢复授权、审批与预算仍需要宿主承担。

选择时，比功能数量更有用的问题是：这套应用由谁负责决定继续？如果多个插件、恢复流程和长期调度器都能触发运行，统一约束会越来越重要。如果宿主本来就有成熟的任务系统，让 Agent Loop 保持较小范围也有价值。

复杂度总要有归属。判断一个框架是否合适，要连同宿主需要补上的部分一起看。

## 设计建议

把这些实现细节落回自己的 Agent，值得先守住十个边界：

1. 分开模型响应、工具批次、对话轮次与长期任务，不共用一个完成标记。
2. 继续运行时留下实际输入或明确原因，避免无法解释的空转。
3. 明确普通工具返回后是否需要模型回访，以及谁能取消这次回访。
4. 将生成截断单独处理，尤其不要直接执行不完整的写入参数。
5. 区分工具结果的提交顺序与外部副作用的执行顺序。
6. 取消时分开尚未派发和已经启动的动作，并保留可核对的结果。
7. 将 idle 与目标完成分开，避免空闲事件无条件触发下一轮。
8. 为请求配置变化留下边界；调度规则可以约束后续派发，不能改写已经发生的请求。
9. 恢复状态时显式判断执行授权，不能仅凭 active 就重新开工。
10. 保留结构化的退出原因，让正常结束、限制、取消和崩溃能被分别解释。

这些约束可以逐项通过故障场景验证：在工具执行中插入新消息，在模型输出中制造截断，在状态保存后中断进程，再检查恢复出来的行为是否仍然符合预期。

## 架构落点

DeepSeek 将模型处理放在 step 内，将当前轮输入收敛放在 turn 内，将普通消息队列交给 driver，再让 Goal 等机制负责更长的推进。Pi 则用内层循环处理工具与 steering，用外层循环承接 follow-up，并让宿主通过回调决定退出。

理解这两套代码后，检查自己的循环可以从一个具体位置开始：找到那条 `return`，向外追问它关闭了哪一层；再向后检查，队列、目标调度器和恢复逻辑里，是否还有谁能重新发起工作。

只有这些入口都能说清楚，“结束”才是一个可验证的状态。

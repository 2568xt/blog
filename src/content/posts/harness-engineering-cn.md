让 Agent 搭一个网站，第一轮写出了页面，第二轮接上了数据，第三轮却开始重新研究项目结构。到了交付时，它说功能已经完成，打开浏览器才发现按钮没有接上事件。这里有三个不同的问题：工作没交接清楚，进度没有可信依据，验收也没覆盖实际使用。

这些问题很难靠一句更强硬的提示词一起解决。Harness Engineering 值得讨论的地方，就在于把它们拆开：哪些信息要跨会话保存，哪些动作必须由程序约束，哪些结果要交给独立检查。

Harness 可以理解为围绕模型组织上下文、工具调用、状态和验证的运行系统。这里关心的是它如何影响一次任务的执行：让下一步有依据，让失败能恢复，让完成声明有证据。

每加一层控制，系统也会多一份成本。今天为某种失败加上的步骤，到下一次模型升级时是否还需要，应该和“怎么加”一起考虑。

## 先把状态交接清楚

一次修改跨过多个会话之后，最容易丢掉的往往不是代码，而是判断：哪条路线已经失败，哪个报错尚未解决，下一步为什么要改这个文件。

因此交接记录不能只写进度。它需要保留当前目标、已验证事实、失败尝试和未解决问题。下一轮应该能据此继续工作，而不必从提交数量推断项目是否接近完成。

上下文工程还要继续决定哪些信息值得读入。工具描述含糊，模型就容易选错参数；返回内容太长，真正的报错会被淹没；历史不断累积，旧计划和已经失效的判断也会占据注意力。按需检索、整理笔记、压缩历史，都是为了让当前判断能用到相关信息。

但文件存在，不代表执行者会读；读过，不代表照着做；照着做过，也不代表结果正确。信息管理与执行控制在这里接上了。

[Anthropic 的长任务实践](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)把开局和后续编码分开：先建立功能清单、环境启动方式和进度记录，再让后续会话逐项推进。新的会话先确认目录、阅读工作记录与 Git 历史、检查现有环境，然后选择下一项工作。收尾时留下可恢复的代码状态和交接说明。

| 失败现象 | 需要留下或检查的东西 |
| --- | --- |
| 做完几项就宣布全部结束 | 完整功能清单，以及每项尚未通过的状态 |
| 下一轮反复研究项目结构 | 启动方法、近期提交、进度与未解决问题 |
| 单元测试通过，实际流程失败 | 浏览器或其他真实环境中的端到端验证 |
| 连续修改后无法定位回归 | 可检查的提交与已知可用的恢复点 |

这里必须区分文件格式和权限。JSON 让清单更容易校验，却不会自动成为防作弊的锁。如果 Agent 仍然可以改功能描述、删验收项，或者未经检查就标记通过，那么换一种格式并没有建立硬边界。真正的约束需要由程序校验、权限或独立验收来执行。

上下文也有类似取舍。压缩历史保留连续性，新会话加交接单则减少旧轨迹的干扰。选择哪一种，要看恢复后的工作质量，而不是认定清空上下文天然更可靠。交接单丢掉了失败证据，新会话照样可能重走弯路。

另一个方向是整理 Agent 能看到的工作环境。仓库里的架构说明、设计决策和质量规则应当能被定位、被维护。入口文档适合当目录，细节按需展开；能自动检查的规则放进测试或检查器，文档与代码脱节时有人负责修正。

“仓库即事实来源”最有用的含义，是把口头共识变成可访问、可追溯的资料。它并不意味着仓库里的内容永远正确，也不意味着接上外部工具的 Agent 只能看仓库。维护这份事实来源，本身就是工作的一部分。

## 并发之前，先拆开工作边界

单个 Agent 能持续工作之后，很容易想到同时开十个。可如果十个执行者都在等同一把锁，或者修改同一个模块，并发只是把等待和冲突一起放大。

[Cursor 的长期自主编码实验](https://cursor.com/blog/scaling-agents)记录了这种问题：扁平协作中的锁会形成瓶颈，执行者也可能回避困难任务，转向风险较低的小改动。系统看起来一直有提交，整体目标却没有相应推进。

他们随后区分规划者和执行者。规划者拆解并追踪任务，执行者聚焦具体工作，完成后返回结果与发现；另有判断环节决定是否继续。值得借鉴的是职责边界与反馈方式，不是把某一种层级结构当成所有任务的固定答案。

交接报告也不能只有“做完了”。它至少需要让接收者知道改了什么、验证了什么、遇到了什么问题，以及哪些地方偏离了计划。否则规划者拿到的只是更多状态标签，仍然看不到全局。

Anthropic 的并行 C 编译器实验还揭示了另一种瓶颈：当所有 Agent 都面对同一个整体失败时，增加人数不能自然拆开诊断。引入 GCC 作为参照、混合不同编译器处理的文件，再缩小失败范围，才把一个全局问题变成了可以分别定位的子问题。

这里的关键是可分解的证据。独立工作区能隔离文件修改，却不能自动隔离问题；只有当不同执行者能各自得到有意义的反馈，并发才可能提高吞吐量。二分缩小范围适用于部分失败，涉及多个文件交互时还需要更细的差异调试，不能指望一次切分解释所有错误。

所以启动子 Agent 之前，先写清楚它负责哪部分、交回什么证据、谁负责合并。如果这些还说不清，增加并发通常只会把未完成的设计推迟到合并阶段。

## 完成声明需要外部证据

按流程跑完和满足需求之间，还隔着一次验收。

静态检查能发现部分结构问题，单元测试能覆盖已写出的行为，端到端测试能验证真实路径。但页面能打开，不代表布局合理；按钮能点击，不代表操作顺序符合用户预期。检查的种类不同，能回答的问题也不同。

[Anthropic 在长应用开发实践中](https://www.anthropic.com/engineering/harness-design-long-running-apps)把生成者和评估者分开，让评估进入迭代过程。评估者需要打开页面、执行操作、观察状态，再把具体失败交回去。相比“请再认真检查一下”，这种反馈让下一轮知道该改哪里。

独立角色仍然不是正确性的保证。评估者也可能宽松、漏看需求，或被同一种解释说服。校准标准、保留实际操作证据、检查不同维度，比单纯多叫一个模型更重要。轮次验收约定可以帮助双方对齐目标，但最终标准仍应服务于用户需求，不能由两个 Agent 协商着把难题删掉。

代码审查里的多路检查也属于这个方向。不同检查路径有机会发现不同问题，结果还需要去重和验证；多数意见只能提供信号，不能代替事实。一条只出现一次但能稳定复现的错误，也不该因为票数少而被忽略。

还有一个更基础的边界：执行者不能通过放宽验收条件制造成功。若修改后的测试变容易了，“全部通过”就失去了原来的含义。关键验收标准需要独立维护，测试变更应当可以审查，验证环境也要有适当隔离。

这不要求普通开发中的测试文件一律不可修改。需求变化时测试本来就可能要改。需要防止的是，把实现和评分标准一起改掉之后，仍把绿色结果当成原任务已经完成的证据。

## 做完加法，还要检验哪些可以删

状态交接、协作调度和结果验证解决的是不同失败。一个任务可能只需要其中很小的一部分，不必先搭出完整框架，再寻找用法。

CLI、Skills、记忆系统和工具接口是否算 harness，各家定义并不完全相同。工程上更有用的判断是：这个组件改变了什么行为，它针对哪种失败，又怎样证明有效。基础设施资源也会改变测试结果，所以比较运行方案时，要把环境差异和控制逻辑差异分开。

Anthropic 后续的实验里，一些旧模型需要的步骤，在更强模型上可以被简化。上下文重置、轮次协调和评估频率，都应该随着实际效果重新考虑。某个组件曾经救过任务，不构成它永久存在的理由。

| 组件 | 加入时要解决的问题 | 重新评估时要观察什么 |
| --- | --- | --- |
| 上下文重置与交接 | 长轨迹干扰判断，跨会话恢复困难 | 移除后是否更容易丢任务、重复探索 |
| 轮次验收约定 | 实现与验收对“完成”理解不一致 | 协调成本是否仍换来更少返工 |
| 独立评估者 | 自检遗漏功能或使用问题 | 不同评估频率下的漏检与成本 |
| 规划与调度 | 重复劳动、等待和全局目标漂移 | 简化分工后吞吐量与冲突如何变化 |

这些判断适合通过消融实验完成：固定任务和其他条件，每次移除一个组件，同时看质量、成本、耗时与失败类型。不能只看一轮成功，也不能在换模型、换资源和换提示词之后，把所有变化归功于架构。

提示词同样需要认真维护。复杂框架搭好之后，职责说明是否清楚仍然会影响系统行为。但这不能推出提示词、架构和模型有一个适用于所有任务的固定重要性排序。

可以把这件事理解为“补偿面迁移”：模型能力变化，外部系统需要补的位置也随之变化。这个说法最实际的用法，是给每个组件记录一个失败案例和一组复测条件。以后删它时，团队不必靠回忆争论当初为什么加。

还有一类工作不会因为某次跑通就结束。文档会过期，代码模式会被重复传播，架构也可能逐渐偏离约定。持续维护与定期检查仍需要预算。组件变少和维护成本变小，不一定同时发生。

## 有些步骤可以删，有些边界需要保留

“补偿模型的短板”还不足以解释整个 harness。有些机制改善执行质量，有些机制承载用户授权。这两类机制的退出条件不同。

上下文整理、规划轮次、评估频率，可以根据实验结果简化。读取什么数据、修改哪个项目、能否对外发布，则来自任务授权，不能因为模型更强就自动放宽。

| 约束的来源 | 例子 | 调整依据 |
| --- | --- | --- |
| 当前能力不足 | 容易丢失进度，需要交接记录 | 同类任务中的恢复质量与重复工作量 |
| 执行成本过高 | 所有改动都走完整评估 | 漏检风险、耗时与调用成本 |
| 用户授权范围 | 允许改本地草稿，尚未允许发布 | 用户对具体行动的授权 |
| 环境中的硬边界 | 受保护分支、只读数据、隔离的验收环境 | 系统责任与权限设计 |

一个容易被忽略的地方，是拒绝也需要可观察。工具只返回“失败”，执行者就无法区分输入错误、暂时故障和权限限制。合理的返回应尽可能说明失败类别、操作是否产生副作用，以及允许的下一步。否则重试机制很可能只是在重复同一个无法解决的问题。

这也是 harness 不能只靠提示词堆叠的原因。提示词负责传达意图，执行层负责兑现边界，工具反馈负责说明发生了什么。三者如果不一致，模型很难从一次失败中形成正确的下一步。

可插入的检查机制适合把这类规则接进流程，但每个检查都要说明自己是否阻断执行、失败后怎样恢复。记录日志的钩子不等于权限检查，发出警告也不等于阻止动作。

对于会主动运行的 Agent，还要把“是否值得行动”纳入判断。没有新事实就安静结束，有明确变化再通知；需要人的决定时，说明具体缺了什么。通知次数和运行轮数都不应成为进展的替代指标。

下一次准备增加一层控制时，先记下它要防住的那个具体失败。等模型升级，再拿同一个失败场景测一次。若收益已经消失，就把步骤删掉；若它承载的是用户授权，就继续把边界留在程序里。

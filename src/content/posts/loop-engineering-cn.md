写一句提示词、等结果、读输出、再补一句，真正消耗人的往往不是提示词本身，而是每一轮都要重新判断：这件事做完了吗，结果可信吗，下一步该怎么走。读完 Addy Osmani 对 Loop Engineering 的讨论后，留下来的不是“提示词过时了”，而是一个更窄、更实际的问题：如果把连续行动交给循环，循环凭什么知道该继续，凭什么知道该停。

循环可以把发现工作、执行工作、验证工作和状态记录接起来。它也会把错误、权限和 token 消耗一起重复放大。因此，设计 loop 的核心不在于让 agent 多跑几轮，而在于给每一轮留下可检查的证据，并把接管条件写清楚。

## 状态应该保存被否定的假设

长循环最常见的失败不是忘记“做到了哪一步”，而是忘记“哪些方向已经证明不对”。只记录“已完成三个任务”，下一轮仍可能重新尝试同一个失败方案；记录“方案 B 因测试 X 失败而放弃”，状态才会成为推理的外部记忆。

这也是 loop 位于单个 agent harness 之上的原因。harness 负责一次运行能看到什么、能调用什么；loop 负责跨运行保存目标、证据和下一步。Markdown 文件、Linear board 或 issue 列表都可以承载这份记忆，但字段至少应包括已验证事实、被否定假设、未解决风险和下一步的停止条件。否则所谓恢复只是在重放猜测。

skills、worktrees、connectors 和 sub-agents 都服务于这个状态闭环：skill 把项目约定写到上下文外，worktree 把并行修改隔离开，connector 把状态带回真实系统，sub-agent 则可以留下独立检查结果。它们不是一张必须集齐的功能清单；只有当某个环节确实需要跨回合保存或交接时，才值得加入 loop。

## 自动化在过滤和报告之间取舍

自动化的诱惑是“每天都生成一份报告”。但 issue、CI 和日志巡检的大多数运行没有值得升级的发现。若每次都推送结果，人最终只是从手动巡逻变成手动清理通知。好的循环首先要能安静地结束空运行，把注意力留给真正有变化的条目。

这会改变自动化的输出定义：结果不一定是一篇总结，也可以是状态文件中的一次有证据的更新，或一个需要人工决定的候选项。规则应放在可版本化的 skill 中，筛选标准、输出字段和验证方式才能随项目一起演进。固定在定时配置里的长 prompt 很快会和代码脱节。

自动化仍然需要人的入口。它负责发现和预处理，不负责替人决定所有优先级；当风险、权限或产品取舍超出规则时，结果应该进入 triage，而不是被循环悄悄吞掉。

## 并行产出会撞上 review 带宽

worktree 解决的是机械冲突：不同 agent 在独立目录和分支上工作，不会直接覆盖彼此的文件。它没有解决判断冲突。并行任务越多，候选 patch、测试结果和解释就越多，最后仍需要有人确认哪些结果可信、哪些应该合并、哪些应该丢弃。

所以并行度的上限不是机器能启动多少 agent，而是人能认真 review 多少结果。超过这个上限，循环只是把文件冲突换成筛选拥堵。比较稳妥的做法是让每个子任务返回统一的证据格式，并在状态里记录合并理由；没有被采用的结果也应留下简短原因，避免下一轮再次浪费计算。

## 独立验证有成本，也有边界

让提出方案的人和检查方案的人分开，是 loop 里最有价值的结构。实现 agent 容易沿着自己的解释继续合理化；独立 verifier 可以对照测试、约束和 rubric 检查遗漏。但每多一个 verifier，就多一轮模型调用、工具调用和等待时间。验证不是免费的保险，应优先用于安全改动、迁移、复杂重构和高回归风险任务。

验证还不能被理解为证明。它只能说明某组检查通过，不能自动覆盖未写进 rubric 的风险。因此状态中应保存验证范围和未覆盖项；“检查通过”后面要能接上“检查了什么”。当验证角色与执行角色共享同一份未经整理的上下文时，独立性也只是形式上的。

## 连接真实工具时，权限必须分层

只能读文件系统的 loop 很快会停在“这里是修复建议”。连接 issue tracker、数据库、CI 或消息系统后，结果才可能进入真实工作流；但每接入一个 connector，就增加一条错误扩散路径。读取外部输入的 agent 不应自动拥有高权限写操作，triage、验证和执行最好分成不同角色。

这也是 plugins 的实际价值：把 skill、connector 和权限边界一起交付，而不是让每个人在自己的机器上重新拼装一套脚本。产品名称会变，边界问题不会变：什么可以自动做，什么必须升级给人，状态怎样留下可追溯记录。

## 停止条件要写成可观察的句子

“继续直到完成”不是停止条件。一个能运行的 loop 至少要能回答：测试是否全部通过，是否还有新的发现，预算是否耗尽，是否连续若干轮没有进展，是否遇到需要人工决定的权限或产品问题。满足条件才停，超出边界就停，不能把停机交给模型当下的感觉。

这也说明 Loop Engineering 改变的是杠杆点，不是责任归属。人的工作从逐回合驱动，移到定义目标、状态字段、验证范围和接管边界。循环真正成熟的标志，不是它能无人值守运行多久，而是它能在证据不足时及时把判断交还给人。

**Ontology 在哲学里通常译为“本体论”，讨论什么存在、存在的事物如何分类，以及它们之间有什么关系。到了计算机和知识工程里，这个词也常译为“本体”或“本体模型”，指对某个领域的概念、关系及约束所做的明确描述。** 两种用法有渊源，但工程实践中的目标更具体：让人和程序对正在处理的事物有一套共同、可检查的理解。[Tom Gruber 对 Ontology 的定义](https://tomgruber.org/writing/definition-of-ontology.pdf)解释了这种从哲学概念到知识建模工具的转变。

例如在一个报表系统里，需要先约定：“报表模板”“导出任务”和“生成的文件”是三种不同的东西。模板规定要查什么、怎样排版；任务是某一次执行；文件是这次执行的产物。它们互相关联，却不能互相替代。说“模板存在”，不能推出“这次任务成功”；说“任务成功”，也不能推出“文件现在仍能下载”。

这就是本文所说的本体建模：**把业务里有哪些东西、各自意味着什么、怎样互相关联，明确地表达出来。** 后面仍会使用 Ontology 这个英文名，但讨论的都是这种工程用法。

对 Agent 来说，只有这层模型还不够。它还需要查询当前事实，并决定下一步行动。可以先记住这三个相连的问题：本体帮助确认“在处理什么”，证据说明“它现在怎么样”，决策规则判断“接下来可以做什么”。下面用一张工单，把这三步真正走通。

## 一句“下载不了”，包含了几个不同的问题

假设用户发来一张工单：“昨天的报表一直下载不了，帮忙重新跑一下。”以下账号、任务编号、状态和规则，都是为解释机制构造的示例，不是某个系统的线上事故。

一个直接的处理办法，是搜索“报表下载失败”，找到操作手册，再执行其中的重试步骤。但用户提供的是一个现象，以及他猜测的解决办法。重新生成报表是否有用，需要继续判断。

如果任务还在排队，应该先看进度；如果生成过程失败，可能需要重试；如果文件已经生成，只是下载链接过期，刷新链接就够了；如果账号没有访问权限，再跑十次也不会解决权限问题。

熟悉业务的人通常会先追问：“哪一个商户？哪次导出？页面提示什么？”这些问题看起来零散，实际上是在定位不同的业务对象。把这套判断交给 Agent 之前，值得先把人脑中默认知道的区别写清楚。

假设最终定位到下面这组对象：账号 U-7 属于租户 T-A，它发起了导出任务 E-204；任务生成文件 F-88，用户通过链接 L-9 下载文件。租户可以理解为系统中彼此隔离的一个客户或组织空间。

## 对象、属性和关系，分别在表达什么

先看“导出任务”和“E-204”的区别。“导出任务”是一种类型，约定这一类事物有哪些信息；E-204 是某一次具体导出，称为这个类型的实例。类似于“订单”与“订单编号 O-1001”的区别。

在这个例子里，任务实例有发起时间、执行状态、查询范围等属性；“E-204 生成 F-88”则描述两个实例之间的关系。属性用于描述一个对象，关系用于把不同对象连接起来。至于某项信息建成属性还是独立对象，需要根据业务选择，不是所有名词都必须画一个节点。

| 概念 | 在这个例子里是什么 | 为什么需要它 |
| --- | --- | --- |
| 类型 | 导出任务、文件、下载链接 | 分清几类事物分别承担什么作用 |
| 实例 | 任务 E-204、文件 F-88 | 把讨论落到这一次实际执行 |
| 属性 | 任务状态为成功，链接有到期时间 | 描述对象的特征与当前状态 |
| 关系 | E-204 生成 F-88，L-9 指向 F-88 | 知道应沿着哪条关联继续查 |
| 约束 | 本例规定链接必须指向一个确定的文件 | 明确什么样的记录才有业务意义 |

[W3C 的 OWL 入门文档](https://www.w3.org/TR/owl-primer/)使用类、个体和属性等概念表达知识，并说明如何用形式化语言描述它们。本文采用的是便于理解的业务说法，不要求把这个例子立即实现成 OWL 模型；先弄清要表达的含义，再选存储方式和工具。

这些概念之所以有用，是因为系统里经常存在“名字一样，意思不同”的情况。任务服务返回的 `success` 可能表示计算完成，下载服务返回的 `success` 可能表示链接签发成功。两处都叫成功，但成功的是不同动作。若只把结果合并成“报表正常”，排查线索就丢了。

还要注意，识别出类型不等于定位到实例。Agent 知道用户在问“导出任务”，仍可能查出昨天的三条记录。它应该结合租户、任务编号或明确的时间范围消除歧义；如果现有信息无法区分，就继续询问。别名和关键词可以帮助找到候选对象，不能代替身份确认。

例如，“导出单”“生成任务”在这个系统里可以是同一类型的别名。但“昨天那份报表”究竟是 E-204 还是 E-205，仍需要事实来确认。这一步确认错了，后续即使每个工具都调用成功，也是在正确地操作错误对象。

## 已经有数据库和知识库，为什么还要建模

数据库里通常已经有任务表和文件表，文档里也写了字段含义。再加一层本体，容易让人觉得只是把已有材料换个名字。

区别可以放到同一个问题上看：Agent 要判断“E-204 已经成功，为什么用户还下载不了”，它需要同时知道任务与文件的关系、状态的含义、下载入口的限制，以及对应信息从哪里取得。单张表可能只保存其中一部分，几份文档则可能使用不同的称呼。

| 材料或机制 | 在这个问题中主要提供什么 |
| --- | --- |
| 数据库与业务接口 | E-204 的记录、F-88 的元数据等具体数据 |
| 文档知识库及检索 | 导出机制的说明、故障经验和接口用法 |
| 本体模型 | “任务”“文件”“链接”的含义，以及它们允许建立的关系 |
| 使用这些约定的知识图谱 | E-204 生成 F-88、L-9 指向 F-88 等具体关联事实 |

这不是四种必须分开购买或部署的产品。数据库设计也能体现业务概念，知识图谱也可以同时存放类型定义与实例事实。这里区分的是它们在问题中承担的角色。

为了便于理解，可以先把本体看成“约定怎么描述业务”，把具体事实组成的图谱看成“按这些约定记录了什么”。本体定义任务和文件之间存在生成关系，某次查询才告诉我们 E-204 具体生成了 F-88。**定义一种关系，与证明这一次关系成立，是两件事。**

对于这个例子，直接查关系表、调用接口，也能取得这些关联，并不一定要部署图数据库。只有关系查询和维护需求确实增长了，才需要进一步比较技术方案。画出一张漂亮的图，不会自动让其中的事实变得正确或实时。

知识检索仍然有用。例如故障说明可以解释某个错误码，帮助 Agent 找到排查思路。本体模型可以帮助限定检索对象：先确认是下载链接的问题，再查链接有效期与刷新规则。这两者可以配合，不必把文档全部改写成节点。

## 模型描述业务，接口提供眼前的事实

到这里，我们知道了一张报表背后有哪些对象，但还不知道 E-204 此刻是什么状态。本体中的类型定义相对稳定，任务和文件的状态却会变化，两者需要连接起来。

一种可行的做法，是在业务对象旁登记它的查询方式。例如，任务编号可以传给任务查询接口，得到状态和文件编号；文件编号可以传给文件服务，得到是否存在及保留期限；下载权限则交给权限服务判断。

这里的重点是“知道去哪儿问”。如果模型里只有一个“文件存在”字段，却没有明确它来自哪个系统、什么时候更新，就很难判断它是否足够新，能不能支持当前操作。

以 E-204 为例，下面是一段刻意简化的查询结果。字段名是本文的示意约定，不属于某个现成 SDK：

```yaml
target: T-A / E-204        # 查询的是哪个租户、哪次任务
source: export-service   # 哪个服务给出的结果
observed_at: 10:00:01     # 本次观察的时间，实际记录需包含日期和时区
state: succeeded         # 生成任务已成功
file_id: F-88             # 这次任务生成的文件
version: 12              # 如果服务提供版本，可用于后续检查
```

读这段结果时，能够确认的是：任务服务在本次查询中报告 E-204 成功，并返回文件编号 F-88。接下来就沿着这个编号查询文件服务。不能省略第二次查询，因为文件可能后来被清理了；任务的历史成功状态，不会因此自动改成失败。

继续假设，文件服务确认 F-88 仍在保留期内，权限服务确认当前账号可以访问，下载服务却报告 L-9 已过期。几次查询合起来，才支持“生成没有问题，当前入口失效”的判断。

这时，“证据”也就不再是一个抽象名词：它是与目标对象关联的实际查询结果，保留来源、时间以及必要的版本信息，能够解释一个判断从何而来。来源字段若由模型自己填写，仍不等于查过对应服务。程序应把真实工具返回与调用记录关联起来，供后续核对。

在 [Palantir 对 Ontology 的描述](https://www.palantir.com/docs/foundry/ontology/overview)中，业务对象与底层数字资产相连，同时还包含动作、函数等机制。这是一个把语义建模接到业务操作上的具体实现。普通业务系统可以借鉴这种连接方式，但不能因为写了对象定义，就认为已经具备整套执行能力。

## 决策结构化：把“为什么这样做”写成条件

现在可以回答这张工单最初的问题了：要不要重新跑报表？

在刚才的查询结果下，重跑没有直接针对故障原因。任务成功，文件存在，用户有权限，只有旧链接失效。这个示例系统若支持重新签发链接，就应进入刷新链接的处理步骤。

所谓“决策结构化”，可以先理解为：把熟练操作员的这段判断，写成明确的输入条件和输出选择。以后再遇到类似工单，就不必让模型仅凭“下载失败”四个字重新猜一次。

下面给出一组示意性的分支。它们用于解释设计，不是适用于所有导出系统的通用规则：

| 当前已经确认的情况 | 下一步选择 | 这样选择的原因 |
| --- | --- | --- |
| 还不能确定是哪次任务 | 补充任务编号或筛选条件 | 不能对不明确的对象操作 |
| 任务仍在执行 | 查询进度，说明当前状态 | 尚无生成失败的证据 |
| 任务失败，且当前允许重试 | 请求一次重试 | 失败发生在生成阶段 |
| 任务成功、文件存在、权限通过、链接过期 | 刷新下载链接 | 需要修复访问入口 |
| 文件存在，但当前账号无权访问 | 进入正常权限处理流程 | 重新生成文件不改变授权 |

把这组判断实现成代码时，它可以叫作 `decision_function`，也就是决策函数。输入是已取得的事实，输出是下一步选择及理由。若仍然只是写在 Markdown 中，让模型参考执行，它就是一份结构化的判断说明；文件名叫“函数”，不会让它自动变成程序校验。

对最常见、含义明确的状态组合，可以用普通条件判断实现。对用户描述的理解、异常信息的归纳，则可以让模型参与。两者需要有清晰的交接：模型提出候选解释，程序查询事实，再对明确的条件作判断。遇到没有覆盖的新状态，应当暴露“当前规则无法判断”，而不是填一个最接近的旧状态。

还有一个细节容易漏掉：缺失信息不是否定信息。文件查询超时，说明现在不知道文件是否存在；返回“在当前查询范围中没有找到”，才是另一种观察。若把二者都写成 `exists: false`，系统就可能在证据不足时选择重新生成。

这也是决策输出应该说明原因的用途。后续接手者需要知道，“暂不重试”是因为任务还在运行、用户没有权限，还是文件服务暂时不可用。只有结论相同，下一步未必相同。

## 从接单到解决，把一条路径走完

把前面的概念放回实际执行顺序，这张工单可以这样推进。

**第一步，定位目标。** Agent 结合用户当前登录身份、所在租户和工单信息，查询昨天的导出记录。如果得到多条候选，就让用户确认具体任务，最终定位到 T-A 下的 E-204。此时只解决了“查谁”，还没有决定“改什么”。

**第二步，取得当前观察。** 查询 E-204 得到成功状态和 F-88；查询 F-88 得到文件仍在；检查当前账号的访问权限；最后确认 L-9 已过期。每一步都沿着已确认的对象编号继续，避免把另一条任务的结果拼进来。

**第三步，选择处理办法。** 将这些观察交给前面的决策规则，命中“刷新链接”这一条。选择结果应同时保留依据：生成已完成、文件仍有效、权限通过、原链接失效。如果任一关键条件没有查到，先补充查询。

**第四步，调用实际工具。** Agent 向下载服务提交“为 F-88 刷新链接”的请求。工具负责把调用传给服务，服务负责检查调用者和文件归属，并按照既有业务规则签发新链接。模型作出正确选择，与服务接受这次操作，是两个不同阶段。

**第五步，核对处理结果。** 假设服务返回新链接 L-10。拿到一串 URL 还不足以关闭工单，系统应在当前用户被授权的范围内检查下载是否可用，并核对文件对应的租户、任务及报表日期。如果只有管理员账号能下载，就还没有验证用户遇到的问题已被解决。

完成后，可以给出这样的说明：“任务 E-204 已生成文件，故障来自旧下载链接过期。已刷新下载入口，并在你的访问权限范围内验证可用。”这句话中的每个结论，都能对应到刚才某一步的观察或执行结果。

如果验证工具只能确认链接可用，不能检查文件内容，就应把结论停在“下载入口已恢复”，不要扩大成“报表内容完全正确”。可下载与统计口径正确，仍需要不同的验证。

这里也能看出“决策”和“流程”的区别：决策回答此刻选择什么，流程把查询、判断、执行、验证按顺序接起来。流程中可以有固定片段，例如签发链接后进行下载检查；也可以有依据事实选择的分支，例如转向生成任务排查。动态决策并不要求废弃所有固定流程。

## 为什么不能让模型说一句“允许”就执行

主路径走通之后，再看执行端需要承担的责任。

如果模型输出“权限已通过”，但它没有实际调用权限服务，刷新链接的接口也不做检查，那么前面的规则只停留在文字层面。模型即使理解了本体，仍有可能漏查、误读或者引用旧结果。

因此，生成下载链接、重跑任务等操作，应继续走业务服务原有的授权和状态检查。[Palantir 的提交条件文档](https://www.palantir.com/docs/foundry/action-types/submission-criteria)提供了一个具体参照：动作提交时可以结合用户、对象和参数设置条件，只有满足全部条件才能提交。这里起作用的是执行机制，而不只是 Agent 读到的一段说明。

再考虑另一个分支：任务确实失败，可以重试。Agent 查到失败后准备调用，另一个操作员却先重跑了它。如果服务只相信 Agent 十秒前拿到的状态，就可能创建第二次重试。

服务需要在执行时确认“这次失败还没有被处理”，并同时标记“已有一次重试正在安排”。这个标记可以理解为占位。检查与占位必须在同一事务或原子操作中完成，意思是其他请求不能插到两者中间，也获得同一份执行机会。基于任务版本做条件更新，是一种可选实现；具体仍要结合调度系统的约定。

网络问题则带来另一种重复：服务已经受理请求，返回却丢了，Agent 不知道刚才是否成功。此时重发同一次请求，应能通过请求标识查回或复用已有操作。这通常称为幂等处理。它解决的是“同一请求再来一次怎么办”，与“业务上是否允许创建一次新的重试”要分开。

这些细节不必全部塞进本体定义里。模型中可以登记动作的前提与接口，具体的权限、并发和重复提交处理，仍由执行服务负责。让每一层承担明确的职责，比把所有要求放进一份提示词更容易逐项验证。

## 一次解决，怎样变成下次能用的知识

这张工单解决后，如果只留下“下载失败，刷新链接即可”，下一次就容易用错。文件已被删除时，刷新链接无效；权限不通过时，也不能照搬这次操作。

更有价值的记录，是保留判断的适用条件：生成任务成功、文件仍有效、当前账号有权限、旧链接过期时，可以尝试刷新入口。再附上本次查询与执行的证据，说明这条经验来自什么情况。

任务 E-204 的日志是一段历史，不能直接当成下一张工单的当前状态。可复用的是判断方法，例如“检查链接有效期之前先确认文件存在”；下一次仍然要重新查询那个用户的实际对象。

在把经验纳入规则之前，可以准备几个固定例子检查它：一个符合条件的正例，一个文件已删除的反例，一个权限不足的反例，再加一个查询超时的例子。这里检查的是系统会选择什么动作、执行后发生什么，而不是要求 Agent 逐字复述同一段解释。

规则变更也需要维护责任。假如下载服务改为永久入口，不再暴露可刷新的短期链接，与旧链接有效期有关的判断就应停用或重写。把规则与对应服务、负责人和验证用例关联起来，才方便在接口变化时找到受影响的部分。

本体在这里的作用逐渐清楚了：它让同一个文件对象能够连接到查询方式、相关动作和处理经验。至于规则评审、测试、版本管理如何实现，仍是系统要额外建设的流程，不能从“已经建模”直接推出。

## 从一个小场景开始，才看得出多做这层是否值得

如果一个系统只有两个接口，输入含义明确，执行顺序固定，直接写一个清楚的程序就可能足够。为它额外建设一套复杂图谱，未必带来收益。

当多个团队对同一业务使用不同叫法，同一个对象分散在几个系统里，排查总要重新确认“这个成功是什么意思”“这份文件对应哪次任务”，显式建模才更可能减少重复劳动。它把原本靠熟悉业务的人临时解释的部分，变成可以共同维护的约定。

即便如此，也可以从本文这一小段关系开始：账号、任务、文件、链接。先定义含义，接上真实查询，写清几个常见分支，再观察系统是否少查错对象、能否说明选择依据、处理结果是否符合工单目标。过程中出现的新问题，再决定要补哪一项定义。

不需要先把整家公司画成一张图。先挑一张“看起来应该重跑，实际上只需刷新链接”的工单，看系统能否沿着事实走到这个结论，也能在文件缺失时选择另一条路。这比节点数量更能说明，本体模型是否真的参与了理解和决策。

假设收到一张工单：“昨天的报表一直下载不了，帮忙重新跑一下。”Agent 搜到一篇导出故障排查文档，看到里面有“重试任务”的步骤，于是准备调用工具。

问题是，“下载不了”可能发生在不同地方：任务还在排队，生成过程失败，文件已经生成但链接过期，或者当前账号无权读取。重跑只适用于其中一部分情况。即使流程执行成功，也可能多生成一份用户没有权限下载的文件。

这个假设案例暴露的缺口，在检索之后、动作之前：系统拿到了相关知识，却还没有把眼前的问题变成一个可以判断的具体对象。

Ontology 与决策结构化的组合，值得关注的正是这一段。用对象及其关系组织知识，再让每个决策明确需要哪些事实、允许进入哪些后续步骤。落到工程上，需要分别回答两个问题：判断依赖什么，以及这些条件由谁检查。

## 先确认是哪一次导出

“报表”“导出文件”“下载任务”可能在不同文档里指向同一类业务，也可能分别对应模板、任务实例和文件对象。把它们全当成搜索关键词，检索结果会很丰富，实际操作的目标却仍然模糊。

可以先建立一小组关系：某个账号发起一次导出，导出使用某个模板和查询范围，任务成功后生成文件，文件再通过下载入口交给用户。每个对象有自己的标识和状态。“任务成功”与“文件可下载”因此成为两个需要分别核对的事实。

这里的 Ontology，可以理解为对业务对象、属性和关系的显式建模。在 [Palantir 的定义](https://www.palantir.com/docs/foundry/ontology/overview)里，这一层还包含动作、函数和动态安全机制，并不只负责描述数据。对 Agent 有用的地方，是把“正在谈哪个对象”与“可以对它做什么”连起来。

但模型认出了对象类型，仍不代表找到了对象实例。知道用户在谈一次导出，还得确认租户、任务编号和时间范围。同一个用户昨天可能导出过三次；只凭“昨天那份报表”选择最近的一条，仍然是在猜。

业务关系也要接到实际可查询的位置。任务状态来自任务服务，文件是否存在来自存储服务，下载权限由权限服务判定。图里写着“任务产生文件”，并不能证明这一次真的产生了文件。它只是告诉排查程序，下一条证据应当去哪里找。

## 证据要能被另一个人重新查到

如果 Agent 填出 `status: success`，这个字段究竟意味着什么？它可能是刚查到的任务状态，也可能抄自昨日的工单，甚至只是模型根据上下文补出的判断。

一份能用于决策的观察，至少要说清对象、来源和观察时间。涉及持续变化的状态时，还应保留可用的版本信息。这样接手的人才能知道：这条结果属于任务 A，而不是同一模板下的任务 B；它反映的是刚才的状态，而不是昨天的缓存。

对这个示例工单，可以把排查拆成下面几项：

| 要回答的问题 | 应当取得的证据 | 单凭它还不能推出什么 |
| --- | --- | --- |
| 用户指的是哪次导出 | 租户、任务编号、请求范围 | 当前用户有权重跑 |
| 生成过程是否结束 | 任务服务返回的状态和更新时间 | 文件仍然存在 |
| 文件是否可用 | 对应文件的存在性和有效期 | 当前账号能下载 |
| 能否重跑 | 当前状态、授权结果、重试规则 | 重跑之后一定成功 |

有些情况下，查不到也是有意义的结果，但必须保留原因。接口超时、权限不足、查询范围内没有记录，不能都压缩成一个空值。否则下一步很容易把“暂时不知道”解释成“对象不存在”，继而创建第二个任务。

字段齐全只能让这些问题更容易检查。即使来源和时间都写在 JSON 里，如果它们仍由模型自由编造，也没有增加可信度。关键观察应由查询工具返回，再与本次调用及目标对象关联；模型负责解释这些结果，执行端不能只相信它重新叙述的一份副本。

## 每次决定一小步

确认对象之后，才适合决定下一步。任务仍在运行，就查询进度；任务失败且满足重试条件，才进入重试；文件存在但下载链接失效，则处理链接。不同证据会把同一张工单带向不同路径。

这里的“决策函数”可以先做得很小：接收当前观察，返回下一步，以及支持这一步的条件。信息不足时，输出缺少哪项证据；证据互相冲突时，保留冲突并转交排查。无需为了让工单看起来有进展，强行选一个动作。

动态决定下一步，也不要求把所有流程交给模型临时生成。获取下载链接、提交一次重试、等待任务结束，都可以封装成稳定的程序。模型处理任务描述和例外情况，程序承接已经明确的动作序列，两者之间通过可检查的参数和结果连接。

这一拆分还有一个维护上的好处。假如只修改“什么状态允许重试”，就可以集中检查这个决策及其用例，不必重写从接单到结束的整篇提示词。代价则是需要有人维护状态含义、服务映射和规则版本；文档分成了节点，维护责任并不会随之消失。

## 真正阻止动作的检查在哪里

在知识文件里写“未确认权限不得重试”，能够指导模型。要让这条要求在运行中生效，还得让执行重试的服务验证调用者、目标对象和当前状态。

[Palantir 的提交条件文档](https://www.palantir.com/docs/foundry/action-types/submission-criteria)给了一个具体参照：动作提交可以结合用户、对象和参数设置条件，只有全部条件满足才能提交。这类执行时检查，与给 Agent 一段操作说明，承担的是不同责任。

沿用导出案例，Agent 在十秒前查到任务失败，调用重试前，另一个操作员可能已经重跑了它。执行端如果仅相信旧的 `failed` 字段，就会接受过期判断。状态检查与重试占位需要在同一事务或原子操作中完成，任务版本的条件更新是其中一种实现。若只是先查询、再无条件提交，两步之间仍然留着并发窗口。

条件检查之后，还要处理重复调用。网络超时并不一定意味着提交失败，Agent 再试一次时，应能通过约定的请求标识查询或复用同一次操作。把“允许重试业务任务”和“允许重发工具请求”混在一起，容易制造额外任务。

这些机制需要分别验证：缺少授权时，服务是否确实拒绝；状态已经变化时，旧请求是否被拦下；同一请求重复提交时，是否只产生约定数量的任务。只检查 Agent 有没有输出“条件满足”，测到的仍然只是它的表达。

## 完成之后，留下哪一条经验

任务服务返回接受重试，只能说明请求已被接受。新任务运行成功，才能说明生成过程结束；用户以自己的权限拿到正确文件，才更接近这张工单的完成条件。记录结论时，应同时保留它对应的任务、环境和观察结果。

知识积累也应沿着这个尺度发生。一次工单因为链接过期而解决，适合留下的是带前提的判断：文件仍有效、权限通过、链接失效时，尝试刷新下载入口。直接沉淀成“下载失败就刷新链接”，会把其他原因一并遮住。

新判断可以先作为待评审的规则变更，配上能复现条件的测试数据。既保留应该进入这条路径的例子，也保留状态不符、证据缺失和权限变化的例子。回归检查关注选择了什么动作、产生了什么结果，不必要求模型每次说出完全相同的话。

规则还需要退出机制。下载服务更换了接口，旧链接的有效期策略被废弃，与之关联的判断就应重新验证或停用。否则知识库越积越厚，Agent 越容易找到一条表达清楚、执行条件却早已失效的经验。

开始建设时，挑一种能查清对象、观察状态、验证结果的工单就够了。先让系统在缺少任务编号时准确停住，在状态变化后撤回旧判断，再考虑覆盖更多业务。图谱有多少节点并不难统计；一个看似合理却缺乏依据的动作，究竟在哪一步被拦住，才是这套结构有没有落到程序里的检查点。
